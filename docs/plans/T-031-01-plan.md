**Feature:** F-BIL-001 (Plan Catalog) · **Story:** US-018-01 · **Milestone row:** T-031 (sub-task 01 of 5, one per US-018-01..05) · **Spec:** FR-018-1/2/6, AC-018-1, EC-018-2, EC-018-4 (EC-018-3 deferred, see §4) · **Size:** S

## 1. Goal

Make "plans are data" provable: one validated shape for a plan row (limits + features + code/name), one named default plan code instead of scattered `"free"` literals, and tests that pin AC-018-1 (exactly three seeded plans, new users on Free), EC-018-2 (schema validation), EC-018-4 (FK blocks deleting a plan in use) and the "new plan = new row" alternative flow. **Exit check:** dotnet test on tests/wa.domain.unit and tests/wa.application.unit, plus the filtered integration run in step 5, are green; no new EF migration is produced (step 6).

### D-1 — One default plan code (FR-018-6, TA-3.4 "never hardcoded")
Add `public const string DefaultCode = "free";` on `Plan` (`src/wa.domain/Plan.cs`). The default plan is a domain fact (the seeded Free row's code), so it lives in wa.domain and both application callers read it (onion rule: application → domain). `ILimitsProvider.GuestPlanCode` (`LimitsProvider.cs:14`) becomes `= Plan.DefaultCode` (kept, so its existing callers compile unchanged). `Signup.cs:64` and `RedeemMagicLink.cs:73` call `_plans.GetAsync(Plan.DefaultCode, …)`. A const field is not an EF-mapped property → no model change, no migration.

### D-2 — `PlanDefinition.Validate(Plan)` — one deep entry point for EC-018-2 (TA-3.2, TA-3.4)
New static class `src/wa.domain/PlanDefinition.cs`, single public method `IReadOnlyList<string> Validate(Plan plan)`; empty list = valid. Every future writer of a plan row (admin plan editor, "launch Pro+" insert) calls it before SaveChanges (validate-then-write, EC-018-2 / F-TRF-011-4 rule). US-018-03 extends the SAME method with PriceJson checks when it adds that column — the signature does not change, so later stories are not blocked. Rules, each producing one human-readable error naming the field:
- `Code`: non-empty, ≤ 32 chars (VARCHAR(32), TA-3.2), contains no `.` (the code is a segment of the limits flag key limits.CODE.KEY, TA-3.4). `Name`: non-empty, ≤ 64 chars (VARCHAR(64)).
- `LimitsJson`: parses (JsonException → error), root is an object; key set equals EXACTLY the LimitsRecord JsonPropertyName set (missing key → error, unknown key → error). The key set is derived by reflection from `LimitsRecord`'s `[JsonPropertyName]` attributes — the same contract `LimitsProvider.BuildFieldMap` uses (`LimitsProvider.cs:43-49`) — so no key literals are duplicated. Each value must be a JSON number that fits the property type (`TryGetInt64` for long, `TryGetInt32` for int; 1.5, "5", true, 3000000000 for an int field → error). Values must be ≥ 0, except −1 for `MaxDownloads` and `ActiveTransfersMax` (the Part-2 ∞ sentinel, `src/wa.domain/LimitsRecord.cs:44-48`); use nameof for those two, not strings. long.MaxValue for maxZipSize is ≥ 0 so it passes naturally.
- `FeaturesJson`: parses, object, key set equals exactly the new `PlanFeatures` JsonPropertyName set, every value is JSON true/false.

### D-3 — `PlanFeatures` POCO (shape contract for FeaturesJson)
New `src/wa.domain/PlanFeatures.cs`, mirroring LimitsRecord's style: bool properties `Ads`, `Scheduling`, `Analytics`, `Branding`, `SsoScim` with `[JsonPropertyName("ads" | "scheduling" | "analytics" | "branding" | "sso_scim")]` (F-BIL-001 technical notes FeaturesJson shape; identical to the seeded JSON at `PlanConfiguration.cs:29`). This task uses it only as the validator's key contract; US-018-05 (feature toggles) consumes it for reads. No behavior beyond the properties.

### D-4 — Guard: no plan-code branching in backend code (US-018-01 happy path 3)
xUnit source scan `tests/wa.domain.unit/Plans/PlanCodeLiteralGuardTests.cs` — runs inside the existing gate, so no new gate script (a .mjs gate would change AGENT.md §4). Walk up from AppContext.BaseDirectory to the directory containing `global.json` (repo root), enumerate `src/**/*.cs` excluding any path segment `bin`, `obj`, `Migrations`, and assert no line matches the regex `"(free|pro|business)"` except in the allow-list `src/wa.domain/Plan.cs` (DefaultCode) and `src/wa.infrastructure/Persistence/EntityConfigurations/PlanConfiguration.cs` (seed data). Failure message lists `path:line` per hit. After D-1 the only other hits today (`Signup.cs:64`, `RedeemMagicLink.cs:73`, `LimitsProvider.cs:14`) are gone — confirmed by grep at plan time. Web code is out of this guard's scope (see §4, ProfilePage).

### D-5 — Tests live where the dependency is real
Validator rules = pure domain unit tests (no DB). Seed rows passing the validator, new plan row → resolver, FK block = Testcontainers SQL (TA-14.3), modelled on `SeedDataIntegrationTest` (SQL only, no Azurite, no HTTP host). AC-018-1 part 2 over the wire = two extra assertions in the existing `SignupEndpointTests` first fact (each fact spins its own containers; a new fact would double that cost).

## 4. Open Questions / Risks

- **EC-018-3 code name + deferral.** Spec says UNKNOWN_PLAN; code comments say PLAN_UNKNOWN (`LimitsStores.cs:5`, `LimitsProvider.cs:16`); NEITHER is in the closed ProblemCodes set (REPO-FACTS §1, 18 members) and no API path maps PlanUnknownException today. Adding a code needs an ADR line (TA-4.1.3 closed list, TA-17). No current endpoint accepts a client-supplied plan code, so this is deferred to US-018-02 (resolver story, which also lists it) — that plan must pick the name (spec: UNKNOWN_PLAN) and add the ADR line. Not escalated now.
- **Plan screen renders from data (AC-018-1 block 2, UI half)** has no surface yet → T-036 (plan screen). Related web literal: `src/wa.web/src/features/profile/ProfilePage.tsx:118` branches on planCode === 'free' for the display name; fixing it needs the plan Name on the profile DTO → belongs to T-036, outside the D-4 guard (src/**/*.cs only).
- **Validator has no production caller yet.** No code path writes Plan rows today (admin edits user plans only, `SetUserPlanCommand`). The validator is the contract the first writer must call; until then it is enforced on seeds by the integration test. Wiring "bad row keeps old value" into the cache read path is US-018-02's call.
- **Guard false positives:** a future legit `"pro"` string (e.g. a UI word in a C# email template) trips D-4; the fix is to route it through data or extend the allow-list with a reviewer-visible comment — never loosen the regex silently.
- **Pro/Business values pending D-07 (EC-018-1)** stay as seeded; the "pending D-07" admin marker is not in this story's ACs → admin plan screen work, not here.
