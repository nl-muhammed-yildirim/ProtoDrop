**Feature:** F-TRF-003 (Recipient page) · **Story:** US-003-05 · **Spec:** AC-003-5 (download limit reached → 410 `MAX_DOWNLOADS_REACHED`), US-005-03 (idempotent Status=3 flip), F-TRF-004 endpoint 7 (download-all-url shares the zip path), AC-010-1 (re-send send-time SupersededBy flip) · **Size:** S
**Architecture:** TA-7.2 (download flow, step 4 guarded increment + flip), TA-4.1.3 (Problem+JSON), TA-2.3 (EF confined to `wa.infrastructure/Persistence`). Gap task from the 2026-11-17 Phase 0 sweep — no story task file; this plan is the contract.

## 1. Goal

Replace the three `Local.Remove(tracked)` "detach" calls with a real detach so a cap-reached mint answers 410 `MAX_DOWNLOADS_REACHED` (never 500) and the singleton context stays healthy for later requests; same for the re-send send path. **Exit check:** the three new integration facts (below) are green, were red on the base commit, and `dotnet test tests/wa.application.unit` stays green.

## 2. Design & Decisions

### Root cause (confirmed in source)
- `src/wa.api/Program.cs:62` registers ONE `WaDbContext` singleton shared by every store (`PublicTransferStore`, `SendStore`, `TransferStore`, …). Entities added/loaded with tracking stay in its identity map for the process lifetime.
- `src/wa.infrastructure/Persistence/PublicTransferStore.cs:64-68` (single-file) and `:112-116` (zip): after the raw-SQL Status=3 flip, `_db.Set<Transfer>().Local.Remove(tracked)`. On an `Unchanged` entity `LocalView.Remove` does NOT detach — it marks the entity **Deleted**. `FileItem → Transfer` is a required FK with `DeleteBehavior.NoAction` (`src/wa.infrastructure/Persistence/EntityConfigurations/FileItemConfiguration.cs:16-20`), so with the transfer's FileItems tracked EF throws the "association … has been severed" `InvalidOperationException` (→ 500 INTERNAL via the global middleware). Without tracked dependents the Deleted entry silently survives and the NEXT `SaveChangesAsync` anywhere (e.g. another transfer's mint at `PublicTransferStore.cs:82`) issues `DELETE FROM [Transfer]` → FK violation → 500, and keeps failing until restart (poisoned context).
- When does the singleton track the transfer? Whenever it was created through this process (draft → finalize → send all go through tracked `TransferStore`/`SendStore` on the singleton). The existing cap tests (`tests/wa.api.integration/DownloadUrlEndpointTests.cs:155`, `tests/wa.api.integration/DownloadAllUrlEndpointTests.cs:141`) seed through a SEPARATE test context (`DownloadUrlEndpointTests.cs:54`), so the app context never tracks the row and the bug never reproduced.
- `src/wa.infrastructure/Persistence/SendStore.cs:51-56`: same pattern after the SupersededBy raw UPDATE. Here the original IS always tracked — `ResendTransferHandler` loads it via the tracked `SendStore.FindByIdAsync` (`src/wa.application/UseCases/Transfers/ResendTransfer.cs:52`, `SendStore.cs:23-24`). `Local.Remove` marks it Deleted and the `SaveChangesAsync` at the end of the SAME method tries to delete the original row → the first send of every re-send draft 500s (never integration-tested: no /resend fact in the tests/wa.api.integration project).

### D-1 — Primitive: `EntityState.Detached` via the ChangeTracker
Set `entry.State = EntityState.Detached` for every tracked `Transfer` entry with that Id, enumerating `db.ChangeTracker.Entries<Transfer>()` (not `Local`, which hides Deleted entries — so the helper also cleans an entry that is already Deleted). Detaching an `Unchanged` principal touches nothing else: Transfer has no navigations (`FileItemConfiguration.cs:16-17` `HasOne<Transfer>().WithMany()`), tracked FileItems keep their FK value and stay `Unchanged`; later tracked reads re-materialize the row with DB values (exactly the intent the original comments state). Rejected: `Local.Remove` (the bug); detaching children too (unnecessary — no fix-up without navigations; widens scope); `ChangeTracker.Clear()` (would drop unrelated in-flight entities of concurrent requests on the shared singleton).

### D-2 — One shared helper inside `wa.infrastructure/Persistence` (TA-2.3)
New `internal static class TransferTrackerExtensions` with `DetachTransfer(this WaDbContext db, Guid transferId)`. Three call sites become one line each; the "why" comment lives once on the helper. `internal` — no new public surface, no port change, nothing in `wa.application` changes (onion rule untouched).

### D-3 — DbContext lifetime stays singleton
Changing the singleton to scoped is the real long-term fix for the whole class of tracker bugs but is an architecture change across every adapter (`Program.cs:62-70`) — out of scope; recorded as an Open Question, not escalated as a blocker (this fix is correct under either lifetime).

### D-4 — Tests reproduce the real trigger: seed through the APP's context
Each new fact builds its own `TestFactory` and seeds via `factory.Services.GetRequiredService<WaDbContext>()` in ONE `SaveChangesAsync` (Transfer + BlobRef + FileItem → all tracked `Unchanged`, exactly the post-finalize state). Health is proven three ways: (a) 410 body code, (b) `appDb.ChangeTracker.Entries()` has no `Deleted` entry, (c) an unrelated follow-up write (another transfer's mint → `SaveChangesAsync`) returns 200 and the capped row still exists with Status 3 (read via `FreshDb()`).

## 3. Implementation Plan

1. **Helper** — CREATE `src/wa.infrastructure/Persistence/TransferTrackerExtensions.cs`:
   ```csharp
   using Microsoft.EntityFrameworkCore;
   using wa.domain;

   namespace wa.infrastructure.Persistence;

   /// <summary>T-003-10: after a raw-SQL UPDATE on a Transfer row, drop any stale tracked copy from the singleton context.
   /// NEVER Local.Remove — on a tracked entity it marks it Deleted (→ "association severed" / DELETE on the next SaveChanges).</summary>
   internal static class TransferTrackerExtensions
   {
       public static void DetachTransfer(this WaDbContext db, Guid transferId)
       {
           foreach (var entry in db.ChangeTracker.Entries<Transfer>().Where(e => e.Entity.Id == transferId).ToList())
               entry.State = EntityState.Detached;
       }
   }
   ```

## 4. Open Questions / Risks

- **Singleton `WaDbContext` (`Program.cs:62`) is the systemic risk**: any future `Local.Remove`/stale-tracking mistake poisons all requests, and concurrent requests share one non-thread-safe context. Moving to a scoped/factory context is an architecture change (every adapter, TA-2.3) — recommend a separate backlog item; NOT changed here, so no escalation is required for this task.
- Other `Local.Remove` uses: grep at plan time found only these three sites in `src/`; Coder re-greps `Local.Remove` after the change (expect zero hits).
- The resend fact exercises a path that has never been integration-tested; if the send fails for an unrelated reason (e.g. outbox publish), compare with `SendEndpointTests` setup before suspecting the fix. If the resend → send flow turns out to be blocked by something outside this task, record it and keep the two download facts (AC-003-5 is the task's core).
- Bodies: the new download facts check `code`/`status` only; byte identity with endpoint 4 is already pinned by `CapReached_410_BodyByteIdenticalToEndpoint4` (`DownloadUrlEndpointTests.cs:196`).
