## KEY REPO FACTS
- Endpoint 22 GET wire shape (exact, Program.cs L578–L614): { items: [{ id (Guid as JSON string), email, planName (string | null — null when no plan row), storageBytesUsed (long), activeTransferCount (int), createdAtUtc }], nextCursor }. q is ONE param — server trims + lowercases and matches AppUser.Email substring CI. limit default 25; reject <=0 or >25 → 400 VALIDATION. Malformed cursor → 400 VALIDATION.
- Endpoint 22 PATCH: /api/v1/admin/users/{id:guid}?planId={guid} — planId from the QUERY STRING (Program.cs L647–L678). SuperAdmin-only (Operator → 403 FORBIDDEN via T-011-01 gate); bad format → 400 VALIDATION; unknown user OR unknown planId → 404 NOT_FOUND (same status family — no client-side distinction needed). Success → 204 No Content, no body. Limits take effect at the NEXT finalize (FR-BIL-001-4) — no server recompute; over-quota downgrades allowed in the UI (US-011-03 alternative flows).
- Endpoint 22 DELETE: /api/v1/admin/users/{id:guid} (Program.cs L680–L704). SuperAdmin-only. Null result (unknown/already soft-deleted) → 404 NOT_FOUND — EC-009-2 idempotency reused, the client treats 404 as SUCCESS (no error). Success → 204 No Content. Reuses T-008 GDPR soft-delete + re-home verbatim (transfers re-homed to anonymous).

The client builds the <select> options from this fixed name→GUID map — a pure constant in usersData.ts. Select value = planName mapped back to its GUID for the PATCH; the row renders planName as the visible label. This is the ONLY way to satisfy "plan cell is a <select> populated from seeded Plan rows" without adding an endpoint (task constraint: only 22 GET/PATCH/DELETE).
