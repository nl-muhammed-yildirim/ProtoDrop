## ASSUMPTIONS / DECISION
- **DECISION:** committed artifact shape — per-alert JSON files under docs/alerts/ + action-group.json + README.md, mirroring T-012-03's docs/dashboards/ precedent (JSON as the auditable record; no bicep at M0 because infra/bicep/main/{env}.bicep does not exist yet — a module would create an infra convention with no other member). Options — A) az CLI create from the committed JSONs (auditable, repeatable); B) portal paste for the one-time dev create with the JSON as the reviewable record. RECOMMEND: A for the action group + metric alerts (az has first-class commands), A via `az rest` for the three log-search rules (no dedicated az command for scheduledQueryRules).
- **DECISION:** rule types — Upload success low / DLQ / 5xx spike as log-search (scheduledQueryRules) because their inputs are closed customEvents or built-in request telemetry, not pre-aggregated metrics; Expiry lag / Email failures as metric alerts on Azure.ApplicationInsights custom metrics; Blob 429s as a platform storage metric alert. This is the only split that keeps every input on a surface M0 already populates (TA-10.5 Serilog → AI requests table; T-056-04 reporter for customMetrics/customEvents).
- **DECISION:** DLQ operator — GreaterThanOrEqual 0 instead of TA-10.3's literal "> 0", because a log-search rule over an empty window returns zero rows (no alert) and strict GreaterThan 0 would never fire; the deviation is documented in the rule file + README and preserves "fires on any dlq_count event".
- **Azure access assumption:** dev reaches wa-dev-ai via the same auth surface as T-012-03's dashboard create (CI-injected KV connection string for telemetry flow; manual az login or AI REST API for rule creation). No local az CLI at plan time.
- **M0 gap is acceptable:** `upload.success_rate` has no code-side emitter — the log-search query over upload_started/upload_completed covers it per the task file DECISION line; if unworkable in dev, escalate (AGENT.md §8), do not add an emitter silently.
- **Dev informational tag:** metricAlerts/scheduledQueryRules have no custom tags property at M0 — "dev: informational (launch traffic is synthetic)" goes into every rule's description; prod severities stay verbatim per TA-10.3 (US-012-03 Edge case).
- **5xx spike link:** no API-health dashboard exists in TA-10.4 — 5xx spike links to Business (closest live tile) and the choice is recorded in the rule description + README; Blob 429s deliberately has no link (task file permits "Business or none").
