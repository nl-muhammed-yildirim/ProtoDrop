# T-004-04 — Cap note: hide Download all + "Files are large" (FR-004-4, AC-004-2)

Folded into the F-TRF-017 branch (user decision 2026-11-17), after T-004-03 (feat 0a1c046).

## 1. Goal

On the recipient page, a multi-file transfer whose server-computed `hasDownloadAll` is false shows an inline muted note "Files are large — download individually." under the file list (no Download all button, per-file buttons unchanged); a single-file transfer shows neither; the exactly-at-cap case keeps the button. Exit check: the three cases in `T-004-04-cap-note-ui.md` hold, pinned by vitest + one application unit test, readable at 360 px (T-017-02 mobile half).

## 2. Design & Decisions

- **D1 — No API change; the cap case is derivable client-side without a limit value.** The server sets `HasDownloadAll: transfer.FileCount >= 2 && transfer.TotalBytes <= limits.MaxZipSize` (`src/wa.application/UseCases/Transfers/GetPublicTransferQuery.cs:96`). With ≥2 files, `hasDownloadAll === false` can only mean "over cap". So the client rule is `files.length >= 2 && !hasDownloadAll` — it never sums bytes and never sees MAX_ZIP_SIZE (task constraint "do not recompute the sum client-side"; golden rule 2 / TA-3.4 untouched; TA-4.2a keeps the server authoritative). No escalation needed.
- **D2 — Equality case is already server-correct** (`<=` at line 96). The existing unit tests cover "exceeds" and "under" (`tests/wa.application.unit/Transfers/GetPublicTransferHandlerTests.cs:83`, `:95`) but not "equals". Add one fact pinning the boundary (exit check 3). No handler change.
- **D3 — Absence is the pattern (FR-004-1).** The existing `{hasDownloadAll && (...)}` block (`RecipientPage.tsx:300`) already omits the button entirely — no disabled variant is introduced.
- **D4 — Placement/styling.** A `<p className="rp-cap-note">` rendered directly after `</ul>` (`RecipientPage.tsx:298`), i.e. "directly under the file list" (F-TRF-004 UI notes, UI-Reference §5.3). Its CSS mirrors the existing muted small-text rules `.rp-download-all-hint` / `.rp-downloads-left` (`recipient.css:116`, `:146`): fg-muted, fs-small tokens (tokens.css), centered, `margin: 0`. Plain static text, no live region (it is present at render, not a state change). At ≤640 px no fixed bar is rendered in the cap case, so nothing overlaps it; normal wrapping keeps it readable at 360 px.
- **D5 — i18n.** No existing key fits (grep of `en.json` shows only `recipient.active.downloadAll` / `preparing*`). New key `recipient.active.capNote` in all 8 bundles (`src/wa.web/src/core/i18n/locales/{de,en,es,fr,it,nl,pt,tr}.json`) — `init.test.ts:52` enforces key parity against `en`.
- **D6 — Endpoint 7 over-cap.** `GetDownloadAllUrlHandler` has no cap check; the 413 lives in `f-zip` (TA-6.6). With the button hidden whenever the server says over cap, the UI cannot reach that path (US-004-03 edge case "double safety"). No change here.

## 5. Open Questions / Risks

- **Future server change risk**: if `hasDownloadAll` ever becomes false for another reason with ≥2 files (e.g. a plan without zip), the note would mis-explain. Acceptable at M0; a dedicated `downloadAllReason` field would be an API shape change (out of scope).
- **Endpoint 7 has no cap check** (only f-zip's 413, TA-6.6). UI hides the button so the path is unreachable from the page; a direct API call would trigger generation that f-zip rejects. Not this task.
- Non-English copy is a best-effort translation; native review can adjust wording without code changes.
