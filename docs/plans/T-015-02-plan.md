# T-015-02 — Profile theme select + live `system` OS tracking (FR-015-4)

TASK: T-015-02 profile theme select persistence + live system-mode OS tracking (milestone task T-027, F-TRF-015, TA-8.2).
GOAL: close the two gaps left by T-015-01 — (a) `ProfilePage.changeTheme` does `removeAttribute('data-theme')` for System mode, but T-015-01 removed the `@media prefers-color-scheme` fallback from CSS, so removing the attribute now falls back to `:root` (light) instead of following the OS; and (b) there is no live `matchMedia` listener, so an OS theme change with the tab open does not switch the app (AC-015-3 / FR-015-4). After this task: System mode follows the OS live; explicit light/dark never follow (EC-015-1); and a subsequent page load resolves to the stored theme before first paint via the existing T-015-01 bootstrap (AC-015-1) because the resolved account theme is persisted to the same localStorage mirror the bootstrap reads.

## KEY REPO FACTS (verified against live source 2026-11-13 — trust over plan prose)
- T-015-01 landed: `src/wa.web/src/styles/tokens.css` defines ALL 14 color tokens per `[data-theme]` scope (`:root` light, `[data-theme='dark']`, `[data-theme='light']`). There is **no `@media (prefers-color-scheme)` block** — the pre-paint script in `index.html` always sets an explicit `data-theme="dark"|"light"` before first paint. So removing the attribute at runtime falls back to `:root` (light), NOT the OS preference. This is the regression this task fixes.
- `src/wa.web/src/core/theme/resolveTheme.ts` (T-015-01) exports a pure, already-tested function: `resolveTheme(stored: 'system'|'light'|'dark'|undefined, prefersDark: boolean): ResolvedTheme` where `ResolvedTheme = 'dark'|'light'`. Explicit account choice wins in both directions; system/absent → OS preference. **Reuse it** — do not re-derive the resolution inline.
- `ProfilePage.changeTheme(next)` (lines 56–80) currently: `if (next === 'system') document.documentElement.removeAttribute('data-theme'); else setAttribute(...)` then `setThemeLocal`, `onThemeChange(next)`, then a fire-and-forget `PATCH /auth/me { theme: next }` whose `.then` calls `onSignedIn({ ...profile, theme: updated.theme })`. The attribute switch and the PATCH both live here.
- `App.handleThemeChange(theme)` (lines 91–96) is the single source of truth for session state: it does only `setSession((s) => s ? { ...s, theme } : s)`. It never writes to localStorage and never switches `data-theme` itself — persistence and the attribute switch are owned by the component that initiated the change (ProfilePage). This is where the mirror must be kept fresh for AC-015-1.
- The session mirror is `core/auth/session.ts`: `StoredProfile = { userId, email, displayName, theme: 'system'|'light'|'dark', planCode }`, persisted under localStorage key `'protoDrop.session'` via `writeSession(profile)`. This is EXACTLY what the T-015-01 pre-paint script in `index.html` reads (`JSON.parse(localStorage.getItem('protoDrop.session'))`). So persisting a fresh profile (with the new theme) to this mirror is all AC-015-1 needs — no bootstrap change required.
- The top bar dropdown ALSO has a theme select (`TopBar.tsx` lines 39–43, wired to `onThemeChange`). It fires callbacks only — it does NOT own a PATCH or an attribute switch (comment line 18: "live-wired via PATCH /auth/me" is T-008-07's original intent; the actual PATCH lives in ProfilePage). So TopBar's select already works for the explicit-choice case via App state, but it relies on App to persist + switch. Fixing `App.handleThemeChange` covers both surfaces at once (EC-015-3: admin uses the same mechanism — no per-area themes).
- **No C# side is touched:** no `.cs` or `.csproj` changes; the per-task dotnet gates just compile.
- **wa.web test environment gotcha:** jsdom has NO `window.matchMedia`. The new App effect will call it on mount in every full-App render (App.test.tsx, ProfilePage.test.tsx's full-App tests). The effect must guard for its absence (`typeof window.matchMedia !== 'function'`), OR the test files must install a stub. Both are needed: the guard keeps production-code safe across environments; the stub is needed where a test asserts live-tracking behavior.
- **wa.web gates (per T-015-01 precedent):** `cd src/wa.web && npm run lint && npm run test:run && npx tsc -b`. `test:run` is non-watch vitest; bare `vitest` enters watch mode and hangs. Plus the dotnet compile-only gates from AGENT.md §4.

## DESIGN & DECISIONS
- **D-1 (single source of truth for the runtime switch):** The attribute switch stays where it already lives — inside each surface's change handler — because both surfaces need to work in isolation (ProfilePage is tested in isolation via `renderProfilePage` with a no-op `onThemeChange`; TopBar is tested only through full-App renders). Specifically:
  - `ProfilePage.changeTheme`: replace the `if (next === 'system') removeAttribute(...) else setAttribute(...)` branch with `const resolved = resolveTheme(next, window.matchMedia('(prefers-color-scheme: dark)').matches); document.documentElement.setAttribute('data-theme', resolved)`. This fixes the System-mode regression in isolation AND keeps the existing "theme change to dark" test (ProfilePage.test.tsx line 149) green — it already asserts `data-theme === 'dark'` after selecting Dark, which still holds.
  - `App.handleThemeChange`: add the same resolved-attribute switch + a `writeSession` mirror write, so that TopBar's dropdown select (which fires only `onThemeChange`) also persists and switches in place. This is what makes AC-015-1 hold for the TopBar path too.
- **D-2 (live OS tracking — FR-015-4 / AC-015-3):** A new hook (src/wa.web/src/core/theme/useSystemTheme.ts) encapsulates the listener. It is called from App with the current theme value:
  ```ts
  export function useSystemTheme(theme: 'system' | 'light' | 'dark') {
    useEffect(() => {
      if (theme !== 'system') return   // explicit light/dark never follow the OS (EC-015-1)
      if (typeof window.matchMedia !== 'function') return  // jsdom/SSR safety — no listener, no throw
      const mq = window.matchMedia('(prefers-color-scheme: dark)')
      const onOSChange = () => {
        document.documentElement.setAttribute('data-theme', resolveTheme(undefined, mq.matches))
      }
      mq.addEventListener('change', onOSChange)
      return () => mq.removeEventListener('change', onOSChange)
    }, [theme])
  }
  ```
  The listener is registered **only while in system mode** (FR-015-4 Technical notes): the early-return when `theme !== 'system'` means no listener exists for explicit choices, so OS changes are ignored. When `theme === 'system'`, each OS change re-resolves via the pure function and sets an explicit attribute — never removing it (there is no @media fallback to fall back onto).
- **D-3 (persistence for AC-015-1):** The resolved account theme must land in the localStorage mirror BEFORE the next paint's bootstrap runs. Two writes, both via `writeSession`:
  - In `ProfilePage.changeTheme`, after a successful PATCH `.then` (the existing `onSignedIn({ ...profile, theme: updated.theme })` call site), add `writeSession(updated)` where `updated` is the server-round-tripped profile. This persists the SIGNED-IN user's choice to the mirror the bootstrap reads.
  - In `App.handleThemeChange`, after computing the new session object, write it back via `writeSession`. This covers TopBar-initiated changes (which don't go through ProfilePage) and keeps the mirror fresh even before the PATCH resolves.
  Both writes are idempotent and cheap; the bootstrap reads whatever is there at paint time.
- **D-4 (no new API surface):** Reuse `PATCH /auth/me` exactly as T-015-02's constraints require — no new endpoint, no schema change. The ProfilePage PATCH already exists and is tested; this task only adds the persistence + listener around it.
- **D-5 (test strategy for matchMedia):** A shared test helper (src/wa.web/src/test/matchMediaStub.ts, new file — see FILES FOR CODER) exports an installable stub with a controllable `matches` flag and a way to fire the change event. App.test.tsx installs it in `beforeAll`/per-test as needed; ProfilePage.test.tsx uses it where a test needs to drive an OS change. The stub is test-only (lives under src/test/, imported only from `.test.*` files) so production code never sees it.
- **D-6 (no bootstrap change):** The T-015-01 pre-paint script in `index.html` already reads the mirror correctly and always sets an explicit attribute. AC-015-1 ("dark applied before first paint after picking Dark") is satisfied by keeping the mirror fresh — no index.html edit needed this task.
- **D-7 (prefers-reduced-motion untouched):** No theme code touches `prefers-reduced-motion` (EC-015-2) — it belongs to F-TRF-016. No assertion needed beyond "theme tests don't break reduced-motion" which is already the case.
