## ASSUMPTIONS / DECISION
- DECISION: q semantics = OR in ONE predicate (t.LinkId == q OR EXISTS EmailRecipient Address LIKE %q%) — satisfies both gherkin cases with one param and no shape sniffing; the documented downside (an 8-char linkId that also substring-matches some email address returns extra rows) is accepted: LinkId is Crockford base32, emails contain @, collision is rare and admin search over-returning is benign.
- DECISION: scope = ALL statuses by default, including deleted (Status=4 / DeletedAtUtc != null) — the screen's job is "find any transfer" incl. abuse-report targets already user-deleted; a status filter ANDs on top of that base set (deleted→{4} still composes).
- DECISION: status vocabulary = per-status values (draft/active/expired/download_limit/deleted), NOT T-009-02's all|active|expired grouping — the admin screen needs per-status filtering (spec: "by status" with 5 states); T-009-02's mapping is user-facing and its UI has no draft/deleted chips.
- DECISION: testability structure = port method with explicit filter args + pure cursor/limit/status/range handling in the handler (mirrors IOverviewStore windows-in style); predicate composition itself sits in the EF query (infrastructure), verified manually — no expression-tree builder, which would be a new idiom in this repo.
- DECISION: minBytes/maxBytes/from/to are optional params on the SAME endpoint 21 (per the task doc's DECISION line) — no renumbering; from is inclusive >=, to is inclusive <=.
