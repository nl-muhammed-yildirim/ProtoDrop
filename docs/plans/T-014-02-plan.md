# T-014-02 — Locale detection order in core/i18n (account → browser → en)

TASK: T-014-02 locale detection order (milestone task T-026, F-TRF-014, TA-8.5).
GOAL: replace T-014-01's stub `resolveInitialLanguage()` in `src/wa.web/src/core/i18n/init.ts` with the FR-014-3 detection order — **account setting (localStorage) → navigator.language → en** — resolved synchronously before first render. ## DESIGN & DECISIONS
- **Detection order (FR-014-3), all synchronous, no network:**
  1. Account setting: read localStorage key `protoDrop.accountLocale` — a plain string, one of the 8 supported codes. Valid → use it (wins over browser, AC-014-3). Missing/invalid/corrupt → fall through. This is the documented override point for the profile switcher; no JSON shape to validate beyond "is it a known code".
  2. Browser: navigator.language (plain, e.g. "de-DE"), take the 2-letter base via `.split('-')[0]`, lowercase. Supported → use it.
  3. Default: `'en'`. Unsupported codes (e.g. `ja`) fall through **silently** — no toast, no ceremony (US-014-02).
- **Supported set = the keys of the existing `resources` object in init.ts** (the 8 bundles already imported). Single source of truth; no new constant list to drift.
- **SSR/test safety:** resolver returns `'en'` when `typeof window === 'undefined'`, and every storage/navigation read is inside try/catch returning `'en'` on any failure — same committed pattern as `core/auth/session.ts`. This keeps App.test.tsx's SSR render (no window) green.
- **Telemetry (app.initialized properties):** the task instruction says put the resolved locale into app.initialized, but that event does not exist in either closed list and both lists fail fast on unknown names — creating it is T-025 scope (telemetry dashboards, TA-10.3). Compliant approach: export a **synchronous accessor** `getResolvedLocale(): string` from init.ts returning the i18n instance's active language (the .language property). When T-025 emits app.initialized, it reads this — locale lands in its properties without any new event, no cross-coupling now. Documented here so the Reviewer can verify the deviation is intentional and spec-compliant.
- **No theme cross-coupling:** do NOT touch index.html's pre-paint theme script or F-TRF-015 anything — separate decision path (US-014-02 edge case). No `document.documentElement.lang` change either: out of scope for this task's exit checks.
- **Key name:** `protoDrop.accountLocale` follows the existing `protoDrop.session` naming convention in core/auth/session.ts. The ASSUMPTION flag in the task file is resolved by this choice (the F-TRF-008 account-locale storage does not exist yet; this key is what its future UI writes).

## TESTS
- **Import-ordering requirement:** init.ts resolves the language at import time. Tests must install their localStorage shim / navigator stubs via `vi.stubGlobal`/`Object.defineProperty` BEFORE a dynamic `await import('./init')`, then reset with `vi.resetModules()` between cases so each scenario re-imports fresh.
- Detection order (FR-014-3), asserting via the imported i18n instance's `.language`:
  - Account setting wins over browser: localStorage `protoDrop.accountLocale = 'nl'` + navigator.language `'de-DE'` → language is `'nl'` (AC-014-3).
  - Guest with supported browser language: no account key, navigator.language `'de-DE'` → `'de'` (before-first-render half of AC-014-1).
  - Unsupported browser language: navigator.language `'ja-JP'` → `'en'`, silently (no exception, no console.error).
  - No browser signal: navigator.language undefined/empty and no account key → `'en'`.
  - Corrupt account value: localStorage `protoDrop.accountLocale = 'bogus'` + navigator.language `'fr-FR'` → `'fr'` (invalid override ignored, falls to browser).
- SSR safety: with window absent (the jsdom env's default for a fresh module import where localStorage is undefined), init imports without throwing and language is `'en'`.
- Telemetry accessor: getResolvedLocale() returns the same value as i18n.language after each scenario.
- Existing tests must stay green untouched: App.test.tsx (SSR render + its own shim), init.test.ts (T-014-01's bundle/parity/fallback assertions — it imports init in an env without localStorage, which now resolves `'en'`, matching its expectations).
