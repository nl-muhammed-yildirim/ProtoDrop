# T-017-02 plan — Mobile download mechanics verification (Safari zip bar, original filenames)

**Task file:** `docs/features/Phase 0-MVP/F-TRF-017/US-017-02-mobile-download/T-017-02-mobile-download-mechanics.md`
**Spec:** FR-017-3, FR-017-5, AC-017-2, EC-017-2, EC-017-4 | related FR-003-10, FR-004-1/5, EC-003-1/3, EC-004-4, US-004-03 | TA-3.6 (SAS matrix), TA-4.2#6/#7
**Scope:** one Content-Disposition hardening on the existing recipient-zip SAS + pinning tests + a manual staging checklist. No new packages, no new delivery pipeline, no TTL/permission change, no wa.web production change.

## 1. Goal

Prove (and pin with tests) that every download the recipient page can trigger today keeps its original filename on mobile, and make the zip SAS carry an explicit `attachment` disposition so iOS Safari / Android Chrome treat all.zip as a download (FR-003-10 "iOS downloads need Content-Disposition fallbacks") — exit check: the boxes below marked "this task" pass; the Download-all UI boxes are BLOCKED on F-TRF-004 client tasks (see §5 DECISION).

## 2. Design & Decisions

**What already holds (grounded, no change):**
- **Per-file original filename (FR-017-3, EC-003-3):** the handler builds `attachment;filename*=UTF-8''<pct-encoded name>` (RFC 5987) at `src/wa.application/UseCases/Transfers/GetFileDownloadUrlQuery.cs:118-119` and signs it into the SAS via `builder.ContentDisposition` (`src/wa.infrastructure/Blob/BlobSasMinter.cs:116-117`). Already pinned at every level: handler unit (`tests/wa.application.unit/Transfers/GetFileDownloadUrlHandlerTests.cs:56`), minter unit (`tests/wa.application.unit/BlobSasMinterTest.cs:71`), Azurite round-trip with a Unicode name (`tests/wa.api.integration/DownloadUrlEndpointTests.cs:259`), and the iPhone-profile Playwright test (`src/wa.web/e2e/mobile.spec.ts:56`). Nothing to add.
- **Download trigger is iOS-safe:** `download()` fetches endpoint 6 then sets window.location.href (`src/wa.web/src/features/recipient/RecipientStore.ts:352`). Top-level same-tab navigation is not popup-gated, so losing the user gesture across the `await` does not matter on iOS Safari (unlike window.open / a programmatic anchor click into a new tab). No `download` attribute (ignored cross-origin) — the signed disposition does the naming. Unit-pinned via the location fake (`src/wa.web/src/features/recipient/RecipientStore.test.ts:37-65`).
- **Zip entry names = original top-level names (FR-004-5):** `zip.CreateEntry(DeduplicateName(file.Name, …))` (`src/wa.workers/ZipFunction.cs:111-112`), no folder prefix; `_1`/`_2` de-dup pinned in `tests/wa.workers.unit/ZipFunctionTests.cs:9-65`.
- **Single-file → no Download all (FR-004-1) + over-cap hides the button:** server-computed `HasDownloadAll: transfer.FileCount >= 2 && transfer.TotalBytes <= limits.MaxZipSize` (`src/wa.application/UseCases/Transfers/GetPublicTransferQuery.cs:96`); client never recomputes (`src/wa.web/src/features/recipient/RecipientPage.tsx:272-275`); pinned by `RecipientPage.test.tsx:175` ("hides Download all for a single-file transfer").
- **EC-017-2 Range resume:** browser-native against the SAS; server side already proven by `src/wa.web/e2e/recipient.spec.ts:154` (EC-003-1). Real-device 4G check is manual (§3 step 4).

**Gap found (the only code change) — D-1: the recipient-zip SAS has no Content-Disposition.** `MintRecipientZip` passes `respContentDisposition: null` (`BlobSasMinter.cs:92-98`), and f-zip uploads all.zip with no HTTP headers (`ZipFunction.cs:122` → `AzureBlobStore.UploadAsync`, default `application/octet-stream`). Browsers currently infer "download" + the name from the URL tail. FR-003-10 asks for explicit disposition fallbacks on iOS, so the zip SAS signs `rscd = attachment;filename*=UTF-8''all.zip` — same RFC 5987 form as per-file, saved name identical to today's (all.zip), so desktop behavior is unchanged.
- **Where:** inside `BlobSasMinter.MintRecipientZip` (infrastructure), as a private const. Rationale (deep module, codebase-design): the minter fully owns the "recipient zip SAS" shape; both callers (`GetDownloadAllUrlQuery.cs:115` and `ZipFunction.cs:91,128`) get it with zero call-site change, and the `IBlobSasMinter` port (`src/wa.application/Ports/BlobSasMinterPort.cs`) and its 4 hand-rolled test stubs stay untouched. Per-file differs only because its filename is data the application layer owns.
- **Not security-shaped:** TTL (30 min), permissions (`r`), scope unchanged (TA-3.6). The rscd is part of the string-to-sign, so it cannot be tampered with.
- **Ripple:** the zip SAS string-to-sign now has a non-empty content-disposition line → the two test re-signers that hard-code it empty must read it (see FILES FOR CODER). The browser's local-Azurite re-signer already forwards `rscd` (`RecipientStore.ts:60,74,80`) — no wa.web change.

**Not in this task (blocked, §5):** the client "Download all" flow is a no-op (`RecipientPage.tsx:115-118`, F-TRF-004 T-004-03 ☐), and the over-cap inline note is unbuilt (T-004-04 ☐). So exit checks for Safari's zip bar, Android Downloads folder, cancelled-zip no-error-state, "Preparing your download…" sticky state and the 360 px cap note cannot be verified yet. This plan does NOT build them (scope creep; they belong to F-TRF-004).
