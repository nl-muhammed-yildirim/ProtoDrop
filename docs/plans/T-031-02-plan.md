**Feature:** F-BIL-001 (Plan Catalog) · **Story:** US-018-02 · **Milestone row:** T-031 (sub-task 02 of 5) · **Spec:** FR-018-5, FR-018-6 (guest half), AC-018-2, US-018-02 AC blocks 1–2 + edge cases, F-BIL-001 technical note "Resolve(null | free) → Free record" · EC-018-3 blocked by DECISION (§4) · **Size:** S

## 1. Goal

Make the single resolver the provable one source of plan limits: Resolve accepts a missing plan code and returns the default (Free) record, a guard test proves no backend code other than the resolver (and the validator/seed) reads Plan.LimitsJson, and AC-018-2 is pinned on real SQL with the seeded pro flag and a 30 s TTL. **Exit check:** dotnet test on tests/wa.domain.unit, tests/wa.application.unit and tests/wa.workers.unit green, plus the filtered integration run of step 5.

### D-1 — Resolve(null | blank) → default plan (F-BIL-001 tech note, FR-018-6, TA-3.4)
Change the port signature to `Task<LimitsRecord> Resolve(string? planCode, CancellationToken cancellationToken = default);` and normalise first thing in `LimitsProvider.Resolve`: `var code = string.IsNullOrWhiteSpace(planCode) ? Plan.DefaultCode : planCode;` then use `code` for the cache lookup, the exception message and the flag prefix. Rationale: a request with no resolved user (guest, or a future PlanContext with no plan yet, US-020-01) must never reach `PlansCache` with a null key (ConcurrentDictionary throws ArgumentNullException) and must never fall back to a literal. No case-folding or trimming of non-blank codes — codes are a seeded closed set (EC-018-3); an odd code stays unknown and fails loudly.
Blast radius: 9 hand-rolled test stubs implement the port with `string planCode`; with the interface parameter now nullable they raise CS8767 (nullability mismatch). Update each signature to `string? planCode` (one-token edit, bodies ignore the argument). No production caller changes: all 6 call sites pass `ILimitsProvider.GuestPlanCode` (`src/wa.application/UseCases/Transfers/CreateDraft.cs:50`, `src/wa.application/UseCases/Transfers/FinalizeTransfer.cs:103`, `src/wa.application/UseCases/Transfers/GetPublicTransferQuery.cs:90`, `src/wa.application/UseCases/Transfers/ResendTransfer.cs:77`, `src/wa.application/UseCases/Transfers/SendTransfer.cs:107`, and `src/wa.workers/ZipFunction.cs:80`).

- `src/wa.domain/PlanDefinition.cs` — validate-then-write (EC-018-2);
- `src/wa.infrastructure/Persistence/EntityConfigurations/PlanConfiguration.cs` — column mapping + seed.
Copy the private FindRepoRoot helper (3 lines) rather than extracting a shared helper — two guard classes do not justify a test-utility module, and T-031-01's file stays untouched. Confirmed by grep at plan time: no other src hit exists (web hits in `src/wa.web/src/core/upload/planLimits.ts:24` are comments in .ts, out of scope).
The literal half ("no number from a literal") is already structural: limit numbers exist only in seed/migration files, and wa.web's client mirror is T-036 territory (§4).

### D-3 — AC-018-2 on real SQL (TA-14.3)

The seed already carries the flag row limits.pro.maxTransferSize = 10737418240 (`src/wa.infrastructure/Persistence/EntityConfigurations/FeatureFlagConfiguration.cs:74`). Build the provider with a 30 s TTL and a test-local mutable clock (a `DateTimeOffset now` captured by the lambda), so expiry is deterministic and never waits on the wall clock.

Neither UNKNOWN_PLAN (F-BIL-001 EC-018-3, US-018-02, US-020-01) nor PLAN_UNKNOWN (F-FND-005 FR-053-2, F-XCT-001 FR-044-2, code comments at `src/wa.application/Ports/LimitsStores.cs:5` and `LimitsProvider.cs:16`) is in the closed list (`src/wa.domain/Errors/ProblemCodes.cs:7-28`, 18 members; TA-4.1.3).
