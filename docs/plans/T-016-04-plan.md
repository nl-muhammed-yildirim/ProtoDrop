### Tab-sequence helper (inline in keyboard.spec.ts):

```ts
/** Presses Tab from current focus until activeElement matches stopSelector; returns array of activeElement identifiers at each intermediate stop (excluding start and stop). */
async function collectTabSequence(page: Page, stopSelector: string): Promise<string[]> {
  const sequence: string[] = []
  let guard = 0
  while (guard++ < 50) { // safety bound — landing has < 15 focusable elements.
    await page.keyboard.press('Tab')
    const active = await page.evaluate(() => document.activeElement)
    if (!active || active === document.body) continue
    const tag = (active as HTMLElement).tagName?.toLowerCase() ?? ''
    const cls = (active as HTMLElement).className ?? ''
    const id = (active as HTMLElement).id ?? ''
    // Check if we've hit the stop element.
    const matchesStop = await page.locator(stopSelector).evaluate((el) => document.activeElement === el)
    if (matchesStop) break
    sequence.push(`${tag}${cls ? '.' + cls.split(' ')[0] : ''}${id ? '#' + id : ''}`)
  }
  return sequence
}
```

For the landing assertion, a simpler approach: Tab from body to `.dz-button` first (skipping TopBar), then record each subsequent stop until `.sl-send`:

## D-2 — Production fix: StagingList.tsx remove-focus

**Bug:** `UploadEngine.remove(fileId)` is a pure state filter (`files.filter(f => f.id !== fileId)`) with no focus management. When the row's `.sl-remove` button is removed from DOM (React unmounts it), browser moves focus to `<body>`.

**Fix location:** `StagingList.tsx` L239-241 — the remove button's onClick handler:
```tsx
// Current:
onClick={() => removeFile(f.id)}

// Fixed: capture next sibling row's remove button (or Send if last row) before removal, focus it after.
onClick={(e) => {
  const rows = Array.from(document.querySelectorAll('.sl-remove'))
  const idx = rows.indexOf(e.currentTarget as HTMLButtonElement)
  const nextTarget = rows[idx + 1] ?? document.querySelector('.sl-send')
  removeFile(f.id)
  // Focus after React re-render — requestAnimationFrame ensures the DOM has updated.
  requestAnimationFrame(() => (nextTarget as HTMLElement | null)?.focus())
}}
```

This is markup-level fix (no positive tabindex). The next row's remove button or Send button receives focus — a sane position per AC-016-1 "remove one".

**Test pin:** Step 2 asserts `document.activeElement.tagName !== 'BODY'` — this passes with the fix, fails without it.

## D-3 — Production fix: LinkScreen.tsx sent-state focus

**Bug:** After `setSendState('sent')`, the ready-state form (with recipients/sender fields) is replaced by the sent-phase block in-place. No mount-focus effect targets the sent-state Copy button → focus falls to `<body>`.

**Fix location:** Add a second ref + useEffect for the sent-state copy button, mirroring T-016-03 D-7's ready-state pattern:

In LinkScreen.tsx:
```tsx
// After existing copyBtnRef (ready state):
const sentCopyBtnRef = useRef<HTMLButtonElement>(null)

// New effect — fires when sendState transitions to 'sent':
useEffect(() => {
  if (sendState === 'sent') {
    sentCopyBtnRef.current?.focus()
  }
}, [sendState])
```

Apply `ref={sentCopyBtnRef}` to the sent-state copy button at L231:
```tsx
<button type="button" className="ls-copy-btn" ref={sentCopyBtnRef} onClick={() => void handleCopy()}>
```

**Test pin:** Step 7 tabs from body (post-swap) to `.ls-copy-btn` — if focus is already on it (from the effect), Tab would move PAST it. So the test should assert: after sent-state appears, `document.activeElement` IS `.ls-copy-btn` (sentCopyBtnRef). No tabbing needed for this step — just verify mount-focus landed correctly.
