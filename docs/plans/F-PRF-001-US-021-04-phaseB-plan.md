**Feature:** F-PRF-001 Custom "From" Branding (Phase 1-Pro) · **Story:** `docs/features/Phase 1-Pro/F-PRF-001/US-021-04-manage-logo.md`
**Scope:** FR-021-3, FR-021-4 (logo half), FR-021-5, AC-021-4, AC-021-5 (UI half), EC-021-2, EC-021-3, EC-021-5. Builds on Phase A (9a87a17: DELETE /auth/me/logo, `IOrgLogoStore`, `LogoContentSniffer`) and the Phase A plan §2.3 outline (`docs/plans/F-PRF-001-US-021-04-plan.md`).
**Decisions:** the five Phase A DECISION blocks were answered **option A** by the user (binding, not re-opened here). The Part 3 log lines are in §5 for the orchestrator.

## 1. Goal

A Pro/Business user can upload an org logo (PNG/JPEG/WebP/SVG, at most MAX_LOGO_SIZE from the Limits Registry) from the profile page, preview it and remove it; an oversized or wrong-type upload is rejected with LOGO_TOO_LARGE / LOGO_TYPE_INVALID and leaves no partial state; the recipient page gets a 30-minute inline read SAS for the logo only while the sender's plan has branding. **Exit check:** the new unit, integration and vitest facts in §3 are green, plus the AGENT.md §4 gate (integration filtered per pitfalls; full run at feature end).

### 2.2 Architect decisions (within AGENT.md §7 autonomy)
- **D-B1 Server-side raw-body PUT** (Phase A §2.3 item 2, TA-4.2a thin endpoint). The endpoint passes `HttpRequest.Body` to `UploadOrgLogoCommand(Guid UserId, Stream Content)`; the **handler** reads at most MaxLogoSize + 1 bytes into memory, so an oversize body is rejected without buffering it and Kestrel's own body cap is never reached. Order: user exists (404) → `PlanContext.Features.Branding` (403 FORBIDDEN, details "Pro plan required.") → size (LOGO_TOO_LARGE, details name the limit in bytes and MB) → sniff (LOGO_TYPE_INVALID) → upload blob at `BlobPaths.OrgLogo(userId)` with the sniffed Content-Type → `IOrgLogoStore.SetPathAsync` → delete the previous blob if the previous path differs. **No partial state:** every rejection happens before any write; if `SetPathAsync` throws and the previous path was not the canonical path, the handler deletes the just-written blob and rethrows (500). When the previous path already equals the canonical path the column is unchanged by the failure, so the new bytes are simply the live logo (documented in §4).
- **D-B2 Gate source.** The upload and owner reads use `IPlanContextAccessor` (TA-3.4, FR-020-5), never `IFeaturesProvider`, so `tests/wa.domain.unit/Plans/PlanFeaturesConsumerGuardTests.cs:16-25` needs **no allow-list change**. The recipient gate stays in the allow-listed `src/wa.application/UseCases/Transfers/SenderBranding.cs` + `GetPublicTransferQuery.cs`.
- **D-B3 Content-Type at write: new narrow port `IBlobContentWriter`** (`UploadAsync(path, content, contentType, ct)`) in `src/wa.application/Ports/BlobStore.cs`, implemented by `AzureBlobStore` via `BlobUploadOptions.HttpHeaders.ContentType`. Adding a parameter to `IBlobStore` would break ten hand-rolled stubs (grep `: IBlobStore` in tests/). Program.cs registers `AzureBlobStore` once and maps both interfaces to it.
- **D-B4 Recipient GET (EC-021-2, EC-021-5).** `SenderBranding.ResolveAsync` returns `SenderBrandingView(string? OrgName, bool HasLogo)`: both empty for guest sends, a missing/deleted owner row, or a plan without branding (EC-021-5: the column is never touched, values kept). The logo does not depend on the org name being set. `GetPublicTransferHandler` then calls `IBlobStore.ExistsAsync(BlobPaths.OrgLogo(owner))`: true → `OrgLogoUrl` = minted SAS; false → `OrgLogoUrl` null + `LogEvent(TelemetryEvents.BrandingLogoMissing)` (property-free, no PII). One metadata HEAD per branded page view; no SAS minted for Free senders. Invariant: `AppUser.OrgLogoBlobPath` is only ever null or `BlobPaths.OrgLogo(userId)` (Phase B writes only that), so the stored path acts as the "has logo" flag and all I/O uses `BlobPaths`.
- **D-B5 Owner read endpoint GET /api/v1/auth/me/logo** → `{ logoUrl, maxLogoSize, brandingEnabled }` (PUT returns the same body). No existing endpoint exposes the logo cap: GET /billing/plan exposes only maxTransferSize/maxSingleFile (`src/wa.api/Program.cs:1382`), and GET /auth/me's key set is pinned (`src/wa.api/Program.cs:1038-1046`; Part 3 2026-11-18 "/auth/me unchanged" precedent). One small endpoint gives the profile section its preview, the server-provided cap and the Free disabled state in one call. The owner preview URL is minted regardless of plan (own data; a downgraded user can still see and remove the kept logo, EC-021-5), via the same `MintOrgLogo`.
- **D-B6 CORS: add PUT** to the preflight allow-methods (`src/wa.api/Middleware/CorsAllowListMiddleware.cs:40`). Without it the browser cannot call the approved PUT route cross-origin (SPA :5173 → API :8080). Origins, headers and credentials are unchanged; no test pins the string. Flagged in §4.
- **D-B7 Old-blob deletion on replace** happens after the DB update and only when the stored path differs from the canonical one (legacy or test paths); a failed delete leaves only an orphan.
- **Web (UI-Reference §5.5, FR-021 UI notes).** New `OrgLogoSection` on the profile page, below the plan line. It is not wrapped in FeatureGate: the plan gate comes from `brandingEnabled` (feature branding AND the plan row, already combined server-side by FeaturesProvider). Drop zone `div role=button` (drag or click → hidden file input, the global `input[type='file']` display none rule), client pre-check against `maxLogoSize` from the server (message names the limit via `formatBytes`, no request sent), preview img 40 × 40 contained with `var(--radius-sm)`, **Remove logo** ghost button (`au-ghost-btn`, 44 px, `src/wa.web/src/index.css:876-885`). On Free: drop zone `aria-disabled`, title "Pro plan required" and a link to PLAN_PATH.

## 4. Open Questions / Risks

- **CORS PUT (D-B6)** touches TA-4.1.6 config. It widens methods for already-trusted origins only and is required by the approved PUT route. If the orchestrator reads it as security-shaped, the alternative is a POST route, which would contradict the approved decision text.
- **Auth rate rule** (`*:/api/v1/auth/*`, 5/min, `src/wa.api/Program.cs:123`): the profile page now makes one more /auth call on mount (GET logo). A user doing GET + several uploads/removes within a minute can hit 429. The rule is not changed (security-shaped); the UI shows the generic error.
- **Replace with DB failure on the same canonical path (D-B1):** the new bytes are live while the request answers 500. Acceptable: the column is consistent with storage, and no half-written state is visible.
- **Account-delete blob cleanup** runs after the soft-delete commits; a blob failure answers 500 for an already-deleted account (retry → 404) and leaves an orphan in a container with no lifecycle rule. No sweep job exists for avatars (out of scope).
- **Email logo:** the notification email still shows the org name only. A 30-min SAS inside a 7-day email would expire (feature technical notes). Not in this story.
- **Story tech note "SAS mint for the put"** is superseded by D-B1 (server-side sniff before store), as recorded in Phase A.
- **Tests that will be stale at feature end if missed:** SeedDataIntegrationTest flag count and plan JSON, PlanCatalogIntegrationTests FreeLimits, the Phase A D-5 unit fact — all listed above.
