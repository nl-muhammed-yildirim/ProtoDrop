# T-013-04 — Degraded-storage row states UI: Implementation Plan

**Task:** FR-013-3, AC-013-2 (both gherkin blocks) + EC-013-2  
**Depends on:** T-013-03 (already landed — 503+INTERNAL detection at block/SAS-mint level)  
**Size:** S

---

## Design Overview

### Upload rows (AC-013-2 block 1)

T-013-03 already tracks `blobUnavailableFlags` in `UploadEngine.ts` and emits `reason:'blob_unavailable'` in telemetry. However, this flag is module-level only — not exposed to the UI layer. StagingList currently renders "Upload failed — retry" for ALL failures regardless of cause.

**Changes needed:**
1. Expose blob_unavailable status per file via UploadEngine state
2. Update StagingList to render degraded-specific message + ghost Retry button when blob_unavailable
3. Add aria-live="polite" announcement on the row state text
4. Move copy to translation keys (TA-8.5 pattern from ErrorScreen.tsx)

### Download rows (AC-013-2 block 2)

T-013-03 already implemented the core logic: RecipientStore sets `downloadErrorFileId` on 503+INTERNAL mint failures, and RecipientPage renders "File temporarily unavailable." in that row. However:
1. Uses role="alert" (assertive) instead of aria-live="polite" per F-TRF-016-3
2. Copy is hardcoded, not a translation key

**Changes needed:**
1. Update RecipientPage to use aria-live="polite" instead of role="alert"
2. Move copy to translation keys

### No global banner (FR-013-3)

The design already satisfies this — states are row-local and self-clearing on success. No changes needed.

## AC/EC Wiring Trace

### AC-013-2 Block 1: Upload rows
```gherkin
When a block upload fails
Then the retry path is used (5 retries, backoff)
And after retries the row shows "Storage temporarily unavailable — retry."
And a per-file Retry button is available
And the other files' rows are unaffected
```

**Implementation:**
- UploadEngine.ts: When blobUnavailableFlags[id] === true on final failure, set file's status to 'failed' AND expose `isBlobUnavailable` in state
- StagingList.tsx: Check `f.isBlobUnavailable` (new field) — if true, render degraded message + ghost Retry button instead of generic "Upload failed"
- aria-live="polite" on the message element announces the state change

### AC-013-2 Block 2: Download rows
```gherkin
Given a recipient page while storage is down at SAS-mint time
When a download is attempted for one file
Then that row shows "File temporarily unavailable."
And the file list still renders and other rows remain actionable
```

**Implementation:**
- RecipientPage.tsx: Change role="alert" to aria-live="polite" on the error message (T-013-03 already handles the logic)
- Move copy to translation keys

### EC-013-2: Self-clearing states
```gherkin
A successful retry clears the state; there is no global banner in MVP
```

**Implementation:**
- UploadEngine.ts: On successful uploadFile completion (status → 'done'), reset blobUnavailableFlags[id] = false
- StagingList.tsx: When status === 'done', render normal row (no error message) — already works via conditional rendering
- RecipientPage.tsx: downloadErrorFileId clears on next successful download attempt (T-013-03 handles this in store)

## DECISION Lines

**DECISION 1:** UploadEngine exposes blob_unavailable as a boolean field on StagedFile, not via separate state map. Rationale: keeps per-file data co-located; matches existing pattern where status/progress are inline fields. Coder adds `isBlobUnavailable?: boolean` to StagedFile interface and sets it in uploadFile's failure path.

**DECISION 2:** Reuse existing --danger CSS token for degraded text color (already defined in :root). No new tokens needed. Rationale: task says "matches F-TRF-001 failed-row treatment" which uses --danger; avoids scope creep.

**DECISION 3:** Use aria-live="polite" instead of role="alert" per F-TRF-016-3. Rationale: task explicitly requires polite announcements; role="alert" is assertive and interrupts screen readers more aggressively than needed for transient row states.

**DECISION 4:** Create a new translation keys object DEGRADED_COPY in a shared location (e.g., src/wa.web/src/core/i18n/keys.ts) rather than duplicating ERROR_COPY pattern per feature. Rationale: both upload and download surfaces need the same copy; T-026 will localize once, not twice. DECISION: If no i18n module exists yet, create it as a minimal keys-only file (no runtime i18next dependency).
