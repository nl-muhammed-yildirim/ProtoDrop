# T-011-07 — SetUserPlanCommand + user force-delete: endpoint 22 PATCH/DELETE /api/v1/admin/users/{id} (FR-011-2, FR-011-5)

TASK: T-011-07 admin users writes — `PATCH /api/v1/admin/users/{id}?planId=` (set a user's plan) AND `DELETE /api/v1/admin/users/{id}` (force-delete). Both SuperAdmin-only (T-011-01 policy table already lists both routes at src/wa.application/UseCases/Admin/AdminRolePolicy.cs L20-21 — no new gate row).
GOAL: US-011-03 happy path 2–3 server-side — admin changes a user Free → Pro (AppUser.PlanId updated; next finalize uses Pro limits, FR-BIL-001-4 "applies to new transfers") and force-deletes a user (T-008 GDPR soft-delete + re-home reused verbatim, reason "admin"); both writes produce an AuditLog row + admin.action event carrying the actor email (FR-011-5).

## KEY REPO FACTS
- Closest analogue to mirror EXACTLY: T-011-05 force-delete — `AdminDeleteTransferCommand` (src/wa.application/UseCases/Admin/AdminDeleteTransferCommand.cs) is a MediatR record returning a nullable result; the thin endpoint in Program.cs L596-617 does gate → sender.Send → null→404 → re-read actor email via IAppUserStore from session → IAuditWriter.WriteAsync(actorEmail, action, entityType, entityId.ToString("n"), details) → Results.NoContent(). Mirror this shape for BOTH writes.
- GDPR soft-delete to REUSE (no new store method): `IAppUserStore.SoftDeleteWithReHomeAsync(Guid userId, DateTime deletedAtUtc, ct) → Task<bool>` (false when user id unknown). Impl at src/wa.infrastructure/Persistence/AppUserStore.cs L51-70 — ONE transaction: ExecuteUpdateAsync Set DeletedAtUtc WHERE Id==userId; re-home transfers Status != 2 (drafts/active/download-limit/deleted go anonymous; expired(2) die via the f-delete-transfers job anyway) → OwnerAppUserId=NULL. SenderName snapshot untouched (FR-002-4). Force-delete = this exact semantics + reason "admin".
- CRITICAL difference from T-011-05: after force-delete the user row is soft-deleted, so `IAppUserStore.GetByIdAsync` (filters DeletedAtUtc == null) returns null — the endpoint CANNOT re-read the email post-delete. The handler must capture the email BEFORE the soft-delete and return it in its result; the endpoint audits from the result (details {email}).
- account_deleted event: the self-delete path DeleteAccountHandler (src/wa.application/UseCases/Auth/MeProfile.cs L158-205) calls SoftDeleteWithReHomeAsync THEN emits `EventType.AccountDeleted` via IEventPublisher (PartitionKey = user.Email, Payload = {userId}, GetCorrelationGuid copied verbatim). Mirror that in the force-delete handler — same store call → same PII-sweep event contract.
- Plan write surface: extend EXISTING T-011-06 port `IAdminUserStore` (src/wa.application/UseCases/Admin/IAdminUserStore.cs, EF impl AdminUserStore over WaDbContext, DI singleton at Program.cs L86) with ONE method SetPlanIdAsync. Only 1 test stub implements it (StubAdminUserStore in tests/wa.application.unit/Admin/GetUsersQueryTests.cs L95) — vs 9 if we extended IAppUserStore.
- Plan validation: `IPlansStore.GetByIdAsync(Guid planId, ct) → Task<Plan?>` returns the row or null, never throws (src/wa.application/Ports/LimitsStores.cs). AppUser.PlanId is a plain column (no migration). Limits take effect at NEXT finalize — no limit recompute here.
- Audit helper: `IAuditWriter.WriteAsync(string actorEmail, string action, string entityType, string? entityId, object? details, CancellationToken ct)` — builds the AuditLog row + emits admin.action. Singleton at Program.cs L77-80. Action strings: "user.plan_changed" (plan) / "user.force_delete" (delete); entityType "user"; entityId = userId.ToString("n").
- MediatR auto-scan (Program.cs L33) registers both handlers — NO new DI entry needed (IAdminUserStore, IAppUserStore, IPlansStore, IAuditWriter all already singletons).

## ASSUMPTIONS / DECISION
- DECISION (store surface): extend EXISTING IAdminUserStore with SetPlanIdAsync rather than a new port or extending IAppUserStore. T-011-05 chose a NEW port because no suitable admin port existed; here T-011-06 already created IAdminUserStore (EF over WaDbContext, in DI), so extending it adds one method, breaks only 1 stub (vs 9 for IAppUserStore), and keeps the admin write on the admin surface. Force-delete needs NO new store method (reuses IAppUserStore.SoftDeleteWithReHomeAsync).
- DECISION (unknown planId): → 404 NOT_FOUND (not 400 VALIDATION). Mirrors MeProfile's null-plan → ForNotFound mapping; IPlansStore.GetByIdAsync returns null, never throws. The admin client picks from seeded rows so this is a defensive path, but the closed-list convention for "id resolves to no row" is NOT_FOUND.
- DECISION (force-delete event): emit account_deleted via outbox PLUS the admin.action audit — NOT minimal. Rationale: same store call as the GDPR self-delete (DeleteAccountHandler) → same PII-sweep event contract, and T-011-05's force-delete also emits a domain event (transfer.deleted) in addition to its audit. Tradeoff documented: handler gains an IEventPublisher dep + GetCorrelationGuid copy; if review prefers minimal, drop the event and keep only the audit.
- DECISION (MediatR vs inline): BOTH writes are MediatR records + handlers (mirror AdminDeleteTransferCommand / GetUsersQuery). The thin endpoint does gate → sender.Send → result mapping (404/204) → audit write inline — exactly T-011-05's shape. Rationale: handler logic stays unit-testable from wa.application.unit (no EF, no HttpContext); the "inline" part in T-011-05 is only the gate + 404 mapping + audit, which we mirror.
- DECISION (response body): both writes return 204 No Content (consistent with the sibling force-delete endpoint and T-011-05; the gherkin verifies the side effect via a follow-up read, not the response).
