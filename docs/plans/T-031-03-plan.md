## 1. Goal

Each Plan row carries its prices as validated data (PriceJson: currency, monthly/annual amount + Stripe Price ID, per-seat monthly for Business), with one domain read model that checkout (T-033) and the plan screen (T-036) will consume, so a price change is a row edit and never a code branch. **Exit check:** dotnet test on tests/wa.domain.unit and tests/wa.application.unit green, filtered integration run of step 6 green, and `dotnet ef migrations has-pending-model-changes` reports none after the new migration.

### D-2 — Price shape POCOs: `PlanPrice` (one new domain file, TA-3.4 style)
New `src/wa.domain/PlanPrice.cs`, mirroring PlanFeatures (`src/wa.domain/PlanFeatures.cs:6-22`) — the JsonPropertyName set IS the key contract the validator derives (no key literals duplicated):
- `PlanPrice`: `Currency` ("currency", string), `Monthly` ("monthly", PlanPriceTier), `Annual` ("annual", PlanPriceTier), `PerSeatMonthly` ("perSeatMonthly", long?) — F-BIL-001 technical notes shape, amounts in minor units.
- `PlanPriceTier`: `Amount` ("amount", long), `StripePriceId` ("stripePriceId", string?).
- `BillingInterval` enum { Monthly, Annual } (the user's toggle, AC-018-4).
- Read model, the ONE entry point consumers use (deep module; checkout and the plan screen never touch the JSON): `public static PlanPrice Read(Plan plan)` (JsonSerializer.Deserialize; throws InvalidOperationException naming the plan code when the result is null), `public PlanPriceTier For(BillingInterval interval)` (switch expression; ArgumentOutOfRangeException otherwise), and on PlanPriceTier `public bool IsWiredToStripe()` = StripePriceId is non-blank (edge case "missing stripePriceId → checkout disabled"; T-033 maps false to "Setting up — try again soon").
- Computed helpers MUST be methods, not properties: PlanDefinition derives key sets from public instance properties (`src/wa.domain/PlanDefinition.cs:119`), so a computed property would become a required JSON key.
- PerSeatMonthly semantics (doc comment): null = not seat-priced; set = monthly price per seat in minor units, seats = users (FR-018-3); checkout bills it as Stripe quantity (T-033). No price is ever computed in app code — Stripe-hosted checkout bills the Price object (US-018-03 technical notes).

### D-3 — Extend PlanDefinition.Validate with PriceJson rules (EC-018-2; signature unchanged, as T-031-01 D-2 promised)
After `ValidateFeatures(...)` (`src/wa.domain/PlanDefinition.cs:36`) add `ValidatePrice(plan.PriceJson, errors);`. Reuse TryParseObject / CheckKeySet / Fields / KeyOf. Rules, one field-naming error each, collected (no early stop):
- root: parses, object, key set exactly the PlanPrice property set (perSeatMonthly is required-but-nullable — the spec shape always lists it);
- currency: JSON string matching `^[A-Z]{3}$` (ISO 4217 shape). No "USD" literal in code — single currency per row at launch is a data fact; multi-currency is a later decision (US-018-03 edge case);
- monthly, annual: JSON object whose key set is exactly the PlanPriceTier set; amount a JSON number that fits Int64 and is ≥ 0; stripePriceId JSON null, or a non-blank string starting with the Stripe price prefix price_ (catches a pasted prod_ product ID). Null is valid — the row is simply not wired to Stripe yet;
- perSeatMonthly: JSON null, or a number that fits Int64 and is ≥ 0.
Use KeyOf over the nameof'd property (e.g. KeyOf(typeof(PlanPrice).GetProperty(nameof(PlanPrice.Currency))!)) or cache the keys in static fields like LimitFields — no repeated string keys.

### D-4 — Seed values: placeholders pending D-07, Stripe IDs operator-set (EC-018-1, D-07 open, D-12 open)
`HasData` in PlanConfiguration gets a PriceJson per row (compact JSON, same style as LimitsJson):
- free: `{"currency":"USD","monthly":{"amount":0,"stripePriceId":null},"annual":{"amount":0,"stripePriceId":null},"perSeatMonthly":null}` — Free is never checked out.
- pro (comment "D-07 placeholder — prices pending D-07; stripePriceId operator-set per runbook (D-12)"): monthly 900, annual 9000, both stripePriceId null, perSeatMonthly null. 900/9000 = the US-018-03 AC example and the D-07 working value $9.
- business (same comment): monthly 1900, annual 19000, stripePriceId null, perSeatMonthly 1900 — D-07 lists "$9 / $19 / $49 (TBD)" without assigning them; $19 is taken as the Business placeholder (§5).
No Stripe Price ID is invented: every seed stripePriceId is null, so checkout stays disabled until the operator creates the Price objects and writes their IDs into the row (data change, no deploy). Not an escalation: D-07 stays open; EC-018-1 explicitly orders placeholders seeded and marked pending.

## 4. Open Questions / Risks

- **Business placeholder price.** D-07 reads "$9 / $19 / $49 (TBD)" for two paid plans; the mapping is not stated. Plan seeds Business at 1900 monthly / 19000 annual / perSeatMonthly 1900 as placeholders. This does not decide D-07 (still open, values are data, EC-018-1 orders placeholders); when D-07 is answered the fix is one data migration + the pinned seed test, no code. Not escalated.
- **Monthly vs perSeatMonthly for Business** — whether Business bills a base monthly plus per-seat, or per-seat only, is a pricing decision bundled with D-07; the shape supports both and T-033 decides the Stripe line items. Flag for the D-07 answer.
- **Annual = 10x monthly** is only a placeholder pattern (from the AC example), not a rule; no code derives one from the other.
- **Docs close-out (orchestrator):** TA-3.2 DDL gains `PriceJson NVARCHAR(MAX) NOT NULL -- PlanPrice JSON (F-BIL-001)`; Part 3 log row for the column (spec-mandated, golden rule 4); runbook step "create Stripe Price objects, write IDs into PriceJson" belongs to T-033 / Preflight P-08.
- **No production writer of PriceJson yet** — like LimitsJson, the validator is the contract the first writer (admin plan editor) must call; enforced today on seeds and in the price-change integration fact.
- **Migration on an existing DB:** AddColumn with default "" then UpdateData fills the three seeded rows; a non-seeded row (none exist outside tests) would be left with "" and fail Validate — acceptable, flagged by SeededPlans_AllPassPlanDefinitionValidation for seeds.
