# T-006-06 Plan — Communication Hub sender reads its connection string

**Feature:** F-TRF-006 (Email) · **Story:** US-006-01 · **Spec:** FR-006-1, FR-006-4, AC-006-1, AC-006-2 · **Size:** S
**Architecture:** TA-6.7 step 3 (send via Communication Hub), TA-0.2 rule 7 (adapter picked by config), TA-9.3 (Communication Hub connection is a Key Vault secret), TA-9.4 (no secrets/PII in logs), TA-13.1 (`Wa:CommunicationHub:Connection` is a required wa-workers setting).
**Task file:** none — gap task approved 2026-11-17 (`docs/Open-Decisions-and-Constants.md` Part 3, line 116). This plan is the contract.

## 1. Goal

The production email sender builds its EmailClient from `Wa:CommunicationHub:Connection` (not from the from-address), and the sender selection reads all three email settings through IConfiguration so that the `__` form Azure Linux hosts use works. **Exit check:** the new `EmailSenderSelectorTests` facts (log, Communication Hub built from a valid fake connection, missing-connection failure, key names pinned) are green, and `EmailLogSenderE2ETests` stays green after its one-line caller update.

## 2. Design & Decisions

### Grounding facts
- `src/wa.infrastructure/Email/CommunicationHubEmailSender.cs:15-17` — the constructor takes only `fromAddress` and calls `new Azure.Communication.Email.EmailClient(fromAddress)`. EmailClient(string) parses a connection string (`endpoint=…;accesskey=…`), so an email address throws at construction. No other `new EmailClient(` exists in `src/` or `tests/` (grep).
- `src/wa.infrastructure/Email/EmailSenderSelector.cs:12-20` — `Create(senderSwitch, fromAddress, loggerFactory)`; "log" → LogEmailSender, else CommunicationHubEmailSender.
- `src/wa.workers/Program.cs:99-103` — the singleton factory reads `Wa:Email:Sender` and `Wa:Email:FromAddress` with Environment.GetEnvironmentVariable and colon names. `Wa:CommunicationHub:Connection` is never read anywhere.
- The email handlers already read config through IConfiguration: `src/wa.application/UseCases/Transfers/SendNotificationEmails.cs:106` and `src/wa.application/UseCases/Auth/SendMagicLinkEmailHandler.cs:95` both read `_config["Wa:Email:FromAddress"]`. The host adds env vars to IConfiguration (`src/wa.workers/Program.cs:20`), and the env-var config provider maps `Wa__CommunicationHub__Connection` to the key `Wa:CommunicationHub:Connection`.
- **The API does not send email.** `src/wa.api/Program.cs` registers no IEmailSender (grep: no match). The magic-link and forgot-password handlers are registered only in the workers host (`src/wa.workers/Program.cs:116-129`). So the API has no miswiring to fix.
- Callers of `EmailSenderSelector.Create`: `src/wa.workers/Program.cs:100`, `tests/wa.api.integration/Events/EmailLogSenderE2ETests.cs:257`, `tests/wa.workers.unit/Email/EmailSenderSelectorTests.cs:17`.
- Functions run on Flex Consumption (`docs/04-production-plan.md:72`), which is Linux only. Linux app-setting names cannot contain `:`; they use `__`. So Environment.GetEnvironmentVariable("Wa:Email:Sender") can never see a value set in Azure.

### D-1: CommunicationHubEmailSender takes the connection string explicitly
New constructor: `CommunicationHubEmailSender(string connectionString, string fromAddress, ILogger<CommunicationHubEmailSender> logger)`. It builds `new EmailClient(connectionString)` and keeps `fromAddress` only as the sender address of each message. The send path (SendAsync) does not change. There is no injectable EmailClient seam: the selector tests prove construction with a fake connection string, and sending is covered by the existing fake-sender handler tests (T-006-02). Adding a seam would be scope creep.

### D-2: The selector reads IConfiguration (one owner of the three keys)
New signature: `EmailSenderSelector.Create(IConfiguration configuration, ILoggerFactory loggerFactory)`. The selector reads `Wa:Email:Sender`, `Wa:Email:FromAddress` (default `no-reply@protodrop.com`, the same fallback as `SendNotificationEmails.cs:106`) and `Wa:CommunicationHub:Connection`. Why this shape:
- It is the deeper module. Program.cs passes two services and knows no key names, and the keys get unit tests (today they are inline top-level code nobody can test, see T-006-05 plan §2).
- It follows how the email handlers next to it already read config (IConfiguration), so it is consistent with the email wiring and works with both `Wa:X` (Windows/local) and `Wa__X` (Linux Azure).
- wa.infrastructure already takes IConfiguration (SbEventPublisher, `src/wa.workers/Program.cs:61-62`), so the dependency rule holds (TA-0.2 rule 7).

### D-3: Missing connection when the sender is not "log" → fail on first use, never a silent fallback
Rules:
| `Wa:Email:Sender` | `Wa:CommunicationHub:Connection` | Result |
|---|---|---|
| `log` | any | LogEmailSender |
| anything else / unset | non-blank | CommunicationHubEmailSender |
| anything else / unset | null / blank | throw InvalidOperationException naming the missing key, no values |

Why not fall back to log: in production a missing Key Vault reference would then quietly "send" every email to the log. EmailRecipient rows would be marked notified and recipients would never get their link (it breaks FR-006-1 / AC-006-1 without any alert). A throw is loud. The error happens when IEmailSender is first resolved (the singleton factory runs lazily, at the first email-function run), not at host start. So the expire/delete jobs keep running, and email messages fail into Service Bus retry and dead-letter (FR-006-4 / AC-006-2 path) where they can be replayed once the setting is fixed. Local dev keeps working with `Wa:Email:Sender=log`, which is already the documented dev switch (F-TRF-006 spec line 69, T-006-01 task constraints). The exception message holds only key names. It never holds the connection value (TA-9.4). A malformed connection string makes the Azure SDK throw at construction; we let that throw propagate unchanged and log nothing.

This is the safe production choice and not a product or security decision, so no DECISION is needed for it. The wording of AGENT.md §5.2 ("log-only sender if unset") is now out of date. See §5 Q-1.

### D-4: Scope boundary on the colon env-var reads
Only the email block (lines 99-103) moves to IConfiguration. The colon-named sibling reads in the same file (`Wa:Blob:*`, `Wa:Jwt:Secret`, `Wa:ServiceBus:ConnectionString`, `src/wa.workers/Program.cs:29-30,49,59`) have the same Linux problem (`WaDb` at lines 25/56 has no colon and is fine). Changing them would change other settings, so it is escalated (§5, DECISION, non-blocking) and not done here.

### Constraints honored
No new package (Azure.Communication.Email 1.1.0 is already in `src/wa.infrastructure/wa.infrastructure.csproj:13`; Microsoft.Extensions.Configuration is already in the workers test graph through the wa.workers project reference). No new env var. No ProblemCode, telemetry or schema change. No real Azure call: EmailClient construction does no network I/O.

2. **Selector** — `src/wa.infrastructure/Email/EmailSenderSelector.cs`: replace `Create` with the D-2 signature and the D-3 table. Shape:
   ```csharp
   public const string SenderKey = "Wa:Email:Sender";
   public const string FromAddressKey = "Wa:Email:FromAddress";
   public const string ConnectionKey = "Wa:CommunicationHub:Connection";
   public const string DefaultFromAddress = "no-reply@protodrop.com";

   public static IEmailSender Create(IConfiguration configuration, ILoggerFactory loggerFactory)
   {
       if (configuration[SenderKey] == "log")
           return new LogEmailSender(loggerFactory.CreateLogger<LogEmailSender>());

       var connection = configuration[ConnectionKey];
       if (string.IsNullOrWhiteSpace(connection))
           throw new InvalidOperationException(
               $"{ConnectionKey} is required when {SenderKey} is not 'log' (set {SenderKey}=log for local dev).");

       return new CommunicationHubEmailSender(
           connection,
           configuration[FromAddressKey] ?? DefaultFromAddress,
           loggerFactory.CreateLogger<CommunicationHubEmailSender>());
   }
   ```

## 4. Risks
- **EmailClient connection-string parsing:** if Azure.Communication.Email 1.1.0 rejects the fake key format, use any base64 accesskey and an https endpoint. The parser checks shape only and does no network I/O. If construction still fails, report it as a deviation; do not add a seam.
- **Lazy failure vs startup failure:** D-3 fails when the first email function resolves the sender, not when the host starts. This is on purpose (other jobs stay up, messages are retryable). The cost is that the misconfig shows up as email-function errors and dead-letters, not as a failed deploy. The DLQ_COUNT alert (FR-006-4) catches it.
