# T-016-02 — Wire live regions into all P0 surfaces + injected-failure E2E

TASK: T-016-02 wire ARIA live regions into every P0 surface (upload list, toasts, password card, recipient page) and add the Playwright injected-failure E2E (F-TRF-016 part 2, milestone task T-027). Consumes T-016-01's `useAriaLive` + `ProgressThrottle`; no new ARIA primitives.
GOAL: overall upload progress is announced politely at exactly 0/25/50/75/100 % (EC-016-1); a failed file announces "{name} failed. Press Enter to retry." and bulk failures collapse to one summary; toasts carry role=status (success) / role=alert (error) from a single source (UI-Reference §4.3); wrong password lands "Wrong password" in role=alert (FR-016-5 — already satisfied, verify not re-implement); the recipient page announces "Downloads left: N" politely after each download and reserves the zip "Preparing your download…" announcement for F-TRF-004; row aria-labels stay the single source of truth for spoken names. ## DESIGN & DECISIONS
- **D-1 Upload-list live region.** In StagingList's upload-list branch (the last return, section.sl), call `const { container: progressLive, announce } = useAriaLive({ priority: 'polite' })` and render `{progressLive}` inside the section (mounted with the screen — exists before any update). Drive announcements from a `useEffect` keyed on overall progress + failure set (see D-2/D-3); never call `announce()` during render.
- **D-2 Progress throttle wiring.** Hold `const throttle = useRef(new ProgressThrottle())`. In a `useEffect([overall.sentBytes, overall.totalBytes])`: if `totalBytes === 0` (no files staged — e.g. after "Send again" reset) call `throttle.current.reset()` and return; otherwise compute `percent = Math.round((sentBytes / totalBytes) * 100)`; call `throttle.current.onProgress(percent)`; when it returns non-null, `announce(i18n.t('landing.staging.uploading', { done: formatBytes(sentBytes), total: formatBytes(totalBytes) }))` (reuse the existing visible copy — no new key). **Grounded fact:** the store recomputes `overall` on EVERY mutation including staging (`totals()` at UploadEngine.ts L73–80, called from addFiles/setProgress/setStatus), so StagingList's effect first fires when files are staged with percent=0 — that is the run-seeding 0 announcement (rule b of T-016-01). This matches the visible `.sl-overall` line, which also renders "Uploading… 0 of N" as soon as files are staged (StagingList.tsx L173–175), so the spoken and visual channels stay in lockstep. The throttle guarantees announcements only at 0/25/50/75/100 and that a 99→100 jump always announces; announcing at 100 resets the run so the next upload re-announces from its own initial 0 tick (the reset-on-empty guard above covers the "remove all files mid-run" edge too).
- **D-3 Failure announcements.** Hold `const prevFailedIds = useRef<Set<string>>(new Set())`. In a `useEffect([files])`: compute current failed ids (`f.status === 'failed'`); `newFailures = current − previous`; then (a) if `newFailures.size === 1`, announce the single file: `announce(i18n.t('landing.staging.failedAnnounce', { name }))` where copy is "{name} failed. Press Enter to retry."; (b) if `> 1`, collapse to ONE summary: `announce(i18n.t('landing.staging.bulkFailed', { count }))` ("{{count}} files failed") — do NOT announce per file; (c) update the ref. This routes bulk updates through a single announcement (US-016-02 Alternative flows). The visible row-level `.sl-failed-msg` + Retry button stay as-is (they are the focusable action, US-016-01).
- **D-4 Toast role mapping — new pure module.** Create `src/wa.web/src/core/ui/toastRole.ts`: a pure (no React) function `toastRole(kind: 'success' | 'error'): 'status' | 'alert'` returning `'status'` for success and `'alert'` for error, single-sourced per UI-Reference §4.3. Replace the hardcoded `role="status"` / `role="alert"` at the three visible toast sites (DropZone L134 & L140 → `toastRole('success')`; StagingList finalize-error L161 → `toastRole('error')`) with this function so roles cannot drift per screen. Colocated unit test proves success→status, error→alert.
- **D-5 Password card — verify only.** The existing inline `<p className="rp-password-error" role="alert">` already satisfies FR-016-5 (role=alert + "Wrong password") and is pinned by RecipientPage.test.tsx L647–649. Do NOT add a second hidden container here — the assertive region appears with its text simultaneously, which is exactly the contract ("the shake is visual sugar, the text is the contract"). Leave it untouched; the E2E/unit tests confirm it.
- **D-6 Recipient-page polite live region + zip scope.** In RecipientPage's active screen (section.rp at line 214), call `useAriaLive({ priority: 'polite' })` and render its container inside the section. Drive two announcements from effects: (a) **Downloads left** — hold `prevDownloadsLeft = useRef<number|null>(null)`; in a `useEffect([downloadsLeft])`, when both previous and current are non-null AND current < previous (the post-download decrement), announce `i18n.t('recipient.active.downloadsLeft', { count: current })` politely, then update the ref. Initial load never announces (previous is null). (b) **Growth panel** — in the existing growth effect (lines 70–76), when `growthPanelVisible` first flips true for this page instance, ALSO announce `i18n.t('recipient.active.growthCta')` ("Send something") politely via the same region — it is a new actionable region. **Zip "preparing":** because F-TRF-004/T-017's client preparing state does not exist yet (handleDownloadAll no-op at L91), reserve i18n key `recipient.active.preparing` = "Preparing your download…" in all 8 locales and leave a clearly-marked TODO comment at `handleDownloadAll` stating that when F-TRF-004 lands its preparing state it must announce this copy exactly once (ref-guarded, not per poll) through this page's polite region. No store field is invented now — see ASSUMPTIONS.
- **D-7 E2E.** New `src/wa.web/e2e/ariaLive.spec.ts` modeled on staging.spec.ts (`{ mode: 'serial' }`, real stack, reuse `makeSparseFiles`/`captureDraft`/`isStagePut`). Install a live-region recorder via `page.addInitScript`: a MutationObserver that appends every textContent change of any `[role=status],[role=alert]` element into a global array (`window.__ariaLog`) — this is what makes the test assert contents DURING the run rather than only final state. Tests: (1) **injected failure** — stage 2 files, abort the first file's stage PUTs after capturing the draft; assert `window.__ariaLog` eventually contains a throttle-point progress announcement AND the failed-file announcement "{name} failed. Press Enter to retry." (asserted by polling with `page.waitForFunction` on the log array, tolerant of timing); (2) **toast roles** — trigger an error toast (over-limit staging shows `.sl-limit-msg[role=alert]`) and a success/info toast (`.dz-toast[role=status]` via paste/skip), assert both `[role=alert]` and `[role=status]` are present in the DOM.

## ASSUMPTIONS / DECISIONS
- **DECISION (zip "preparing" scope):** F-TRF-004/T-017 delivered only the server endpoint — `handleDownloadAll` at RecipientPage L91 is still a no-op and no client preparing state exists. T-016-02 therefore reserves i18n key `recipient.active.preparing` in all 8 locales and leaves a TODO at the handler; it does NOT invent store state or wire live polling. The "announced exactly once, not per poll" behavior is satisfied by the page's ref-guarded announce pattern (D-6) that F-TRF-004 client work will call into. Full zip E2E lands when F-TRF-004 client lands; T-016-02's E2E covers progress + failure + toast roles.
- **DECISION (password card):** FR-016-5 is already satisfied by the existing inline `<p class="rp-password-error" role="alert">`; verify rather than re-implement, to keep RecipientPage.test.tsx L647–649 green and avoid a duplicate assertive region.
- **DECISION (progress copy):** reuse the existing `landing.staging.uploading` ("Uploading… {{done}} of {{total}}") for live-region announcements — no new key, keeps parity simple; the throttle (not the copy) is what EC-016-1 pins.
- **ASSUMPTION:** the E2E injected-failure test asserts live-region contents by polling a MutationObserver log (`window.__ariaLog`) with `waitForFunction`, tolerant of upload timing — this satisfies "asserted during the run, not just final state" without flaky fixed-delay waits.
