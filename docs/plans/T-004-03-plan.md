## 1. Goal

Clicking **Download all** calls endpoint 7; a cached zip (200) downloads in one round-trip with no preparing UI, a 202 shows "Preparing your download…" (spinner, disabled) + the polling hint and re-polls at the server's pollAfterSec until 200, and 3 minutes of 202s (or any non-terminal failure) reverts to idle with a role=alert toast "Download preparation failed — try again" — exit check: the vitest cases in step 4–5 pass and `npm run lint && npm run test:run && npm run build` is green.

## 2. Design & Decisions

**Server side already exists (grounded, no change):** endpoint 7 is mapped at `src/wa.api/Program.cs:448`; handler `src/wa.application/UseCases/Transfers/GetDownloadAllUrlQuery.cs:71-128`. Wire shapes (TA-4.2#7):
- 200 `{ url }` — zip exists; the server already counted the download (RecordZipDownloadAsync, +1) and emitted download_started (`GetDownloadAllUrlQuery.cs:107-123`).
- 202 `{ pollAfterSec }` — zip missing, f-zip triggered fire-and-forget (`GetDownloadAllUrlQuery.cs:126-128`). Re-polling is idempotent (f-zip returns the existing zip if present, TA-6.6 step 2).
- 404/410 Problem+JSON with `TRANSFER_EXPIRED` or `MAX_DOWNLOADS_REACHED` (same bodies as endpoint 4); 401 `UNAUTHENTICATED`; 503 `INTERNAL` (`Program.cs:462-472`).
So the F-TRF-004 table's T-004-01/02 ☐ boxes are stale bookkeeping, not missing code (orchestrator close-out item, §5).

**D-1 — the flow lives in the store, as one new action `downloadAll(linkId)`** (TA-8.2: feature self-contained; mirrors `download()` at `src/wa.web/src/features/recipient/RecipientStore.ts:320-385`). The page only renders state. New state:
- downloadAllPhase: 'idle' | 'requesting' | 'preparing'. 'requesting' = a first request is in flight: button disabled (no double mint) but its label stays "Download all" → the cached path never shows the preparing state (US-004-02, exit check 2). Only a 202 moves to 'preparing'; it stays 'preparing' across polls.
- downloadAllFailed: boolean — drives the toast; cleared when a new downloadAll starts.

**D-2 — poll interval is endpoint-driven** (task constraint "do not hard-code an interval table"): the next poll is scheduled after `body.pollAfterSec * 1000` ms. Fallback when the field is missing / non-positive: a named const DEFAULT_POLL_AFTER_SEC = 2 citing FR-004-6 (spec literal, same value the server sends). **3-minute ceiling:** named const ZIP_PREPARE_TIMEOUT_MS = 180_000 citing US-004-01 alt flow. Neither is a plan limit — the Limits Registry (TA-3.4, `docs/Open-Decisions-and-Constants.md` Part 2) holds only per-plan MAX_* / quota values; these are UX timing constants of the same class as the existing LOAD_TIMEOUT_MS (`RecipientStore.ts:31`). No escalation needed. The ceiling is measured from the FIRST 202 (preparingStartedAt); after each 202, if `Date.now() - preparingStartedAt >= ZIP_PREPARE_TIMEOUT_MS` → fail, else schedule the next poll.

**D-3 — outcome mapping per response:**
| Response | Store effect |
|---|---|
| 200 `{url}` | `window.location.href = await browserDownloadUrl(url)` (same Azurite re-sign + same-tab navigation as per-file, `RecipientStore.ts:352`; iOS-safe — no popup gate, attachment disposition from the SAS; T-017-02 adds rscd). Then completion (D-4), phase → 'idle'. |
| 202 | phase → 'preparing'; timeout check; schedule next poll. |
| terminal Problem (classifyProblem, `RecipientStore.ts:113-124`) | `set({ ...LOADING_SHAPE, status, terminalMessage })` — same precedence as per-file (`RecipientStore.ts:337-341`). |
| any other non-ok (401, 503, junk) / network error / ceiling hit | phase → 'idle', downloadAllFailed → true (one failure copy — spec defines only this toast; per-file rows stay usable as fallback, EC-004-4). |
| AbortError (reset/unmount) | nothing. |

Each request gets its own AbortController + LOAD_TIMEOUT_MS timer (per-file idiom). Module-level `downloadAllController` and `downloadAllTimer` (poll setTimeout handle) let `reset()` and a new `downloadAll` cancel everything — no state write after unmount (UploadEngine hermetic-reset convention, `RecipientStore.ts:315-319`).

**D-4 — zip completion reuses the per-file completion path** (comment at `RecipientStore.ts:363-365` and the `RecipientPage.tsx:118` note anticipate exactly this): extract lines 366-375 into a module-private helper `markCompleted(fileIds: string[])` operating on get/set, called by `download()` with `[fileId]` and by `downloadAll()` with every fileId → the growth panel flips via the existing predicate. downloadsLeft decrements by 1 when finite (server counted one zip download). Telemetry: trackClientEvent('download_completed', { fileId: null, bytes: sum of sizeBytes, durationMs }) — closed name (`src/wa.web/src/core/telemetry/clientTelemetry.ts:16-22`); fileId null mirrors TA-7.2 "fileId=null for download-all". The per-file path's behavior must stay byte-identical (incl. its existing `downloadingFileId` handling at L362 — see §5).

**D-5 — page rendering** (`RecipientPage.tsx:115-119, 273-275`):
- Same single `.rp-download-all` button (EC-016-3 / T-003-08 one-element-two-positions; its ≤640 px fixed position at `recipient.css:251-260` is untouched, so the sticky bar shows the spinner + disabled state on mobile for free). `disabled={downloadAllPhase !== 'idle'}`, `aria-busy` true while preparing. Preparing label: `<span className="rp-spinner" aria-hidden="true" />` + i18n recipient.active.preparing (key already in all 8 bundles, `src/wa.web/src/core/i18n/locales/en.json:85`).

Update the header doc comment (T-004-03 line). Shape:
   ```ts
   downloadAll: (linkId) => {
     cancelDownloadAll() // aborts controller + clears poll timer
     const startedAt = Date.now()
     let preparingStartedAt: number | null = null
     set({ downloadAllPhase: 'requesting', downloadAllFailed: false })
     const fail = () => set({ downloadAllPhase: 'idle', downloadAllFailed: true })
     const poll = async (): Promise<void> => {
       const controller = new AbortController()
       downloadAllController = controller
       const timer = setTimeout(() => controller.abort(), LOAD_TIMEOUT_MS)
       try {
         const token = readUnlockToken(linkId)
         const url = DOWNLOAD_ALL_URL_ENDPOINT.replace('{linkId}', linkId)
           + (token !== null ? `?t=${encodeURIComponent(token)}` : '')
         const res = await fetch(url, { signal: controller.signal, headers: { traceparent: getTraceParent() } })
         if (res.status === 202) {
           const body = (await res.json()) as { pollAfterSec?: number } | null
           const now = Date.now()
           preparingStartedAt ??= now
           if (now - preparingStartedAt >= ZIP_PREPARE_TIMEOUT_MS) { fail(); return }
           set({ downloadAllPhase: 'preparing' })
           const sec = typeof body?.pollAfterSec === 'number' && body.pollAfterSec > 0 ? body.pollAfterSec : DEFAULT_POLL_AFTER_SEC
           downloadAllTimer = setTimeout(() => { void poll() }, sec * 1000)
           return
         }
         if (!res.ok) { /* classifyProblem → terminal set; else fail() */ return }
         const body = (await res.json()) as { url: string }
         window.location.href = await browserDownloadUrl(body.url)
         // download_completed (fileId null, summed bytes, durationMs = Date.now() - startedAt), markCompleted(all fileIds),
         // finite downloadsLeft - 1, then set({ downloadAllPhase: 'idle' })
       } catch (err) {
         if (!(err instanceof Error && err.name === 'AbortError')) fail()
       } finally { clearTimeout(timer) }
     }
     void poll()
   },
   ```

That is server behavior from T-004-02 and is not changed here (risk noted for T-017 load checks).
- **Fake timers + crypto.subtle:** only the ceiling / reset tests use fake timers (no navigation); success paths use real timers with a tiny stubbed pollAfterSec.
- No escalations: no package, no limit value, no PII/security change, no new env var.
