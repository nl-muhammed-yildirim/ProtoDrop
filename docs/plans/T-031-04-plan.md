# T-031-04 Plan — Plan changes apply at the next finalize (US-018-04)

**Feature:** F-BIL-001 (Plan Catalog) · **Story:** US-018-04 · **Milestone row:** T-031 (sub-task 04 of 5) · **Spec:** FR-018-4, AC-018-3, US-018-04 AC blocks 1–2 + edge cases, EC-007-1 (F-TRF-007), FR-005-1 (expiry is set on send) · **Size:** S
**Architecture:** TA-3.4 (limits resolved per request via ILimitsProvider, 30 s cache), TA-3.2 (Transfer.ExpiresAtUtc / MaxDownloads columns already exist — no schema change), TA-5.3 (plan.changed is emitted by the Stripe webhook, F-BIL-002 — not here), TA-14.3 (Testcontainers SQL). Golden rule 2: no literal limit values.

## 1. Goal

"Apply at next finalize" becomes one named domain rule that stamps the send-time limits (retention and download cap) onto a draft exactly once, so live transfers never re-resolve and the next send picks up whatever the plan/flags resolve to then. **Exit check:** dotnet test on tests/wa.domain.unit and tests/wa.application.unit green, plus the filtered integration run of step 4 green (Docker running).

## 2. Design & Decisions

### What exists vs what is missing (grounded at plan time)
- **Limits are resolved at the enforcement points, per request (correct, TA-3.4):** CreateDraft (`src/wa.application/UseCases/Transfers/CreateDraft.cs:50`), finalize account checks (`src/wa.application/UseCases/Transfers/FinalizeTransfer.cs:103`), send (`src/wa.application/UseCases/Transfers/SendTransfer.cs:107`). All pass ILimitsProvider.GuestPlanCode (= Plan.DefaultCode, `src/wa.application/Limits/LimitsProvider.cs:14`) — no handler resolves the owner's plan yet.
- **Retention snapshot exists:** send sets `transfer.ExpiresAtUtc = now.AddDays(limits.RetentionDays)` (`SendTransfer.cs:136`) and the expiry job reads the stored column — live rows keep their send-time retention.
- **Download-cap snapshot is missing:** the column exists (`src/wa.domain/Transfer.cs:13`) and the download guards read only the row (`src/wa.infrastructure/Persistence/PublicTransferStore.cs:53,99`), but the value is the finalize literal `MaxDownloads = 1` (`FinalizeTransfer.cs:143`; resend draft `ResendTransfer.cs:93`) and send never overwrites it. So every transfer carries cap 1, not the plan's MAX_DOWNLOADS (Part 2: Free 100 / Pro 1000 / Business -1) — the "same download cap" half of AC-018-3 has nothing to keep. **This is the gap T-031-04 closes.**
- **No new column is needed:** US-018-04 technical notes name the storage — "stored where they matter (ExpiresAtUtc, MaxDownloads) — no re-resolution of live rows". Both columns exist (TA-3.2). No migration.

### D-1 — Named rule: `SendTimeLimits.Stamp` in wa.domain (US-018-04 goal "a rule with a name")
New `src/wa.domain/Transfers/SendTimeLimits.cs` (namespace wa.domain.Transfers, next to CursorCodec), static class, one public method:
`public static void Stamp(Transfer transfer, LimitsRecord limits, DateTime nowUtc)`
- Guard: `transfer.Status != 0` (not a Draft) → throw InvalidOperationException naming the transfer id and "send-time limits are stamped once; live transfers never re-resolve (FR-018-4)". Nothing is written on a throw.
- Writes `transfer.ExpiresAtUtc = nowUtc.AddDays(limits.RetentionDays)` and `transfer.MaxDownloads = limits.MaxDownloads` (the -1 unlimited sentinel is copied as is; the guards at PublicTransferStore.cs:53 already treat `MaxDownloads < 0` as unlimited).
- Does not change Status — the handler still owns the 0 → 1 transition.
- Doc comment: "send-time limits" = the values ILimitsProvider resolves at send, not at page render (US-018-04 edge case); plan switches and limit-flag edits follow the same rule because both only change what the next Resolve returns.
Dependency rule holds: domain → domain (Transfer, LimitsRecord). Deep-module tradeoff: a two-line body, but it is the single seam both halves of AC-018-3 go through, and the guard makes "no re-resolution of live rows" executable instead of a comment.

### D-2 — SendTransferHandler calls the rule (the only send-time stamping point)
Replace `SendTransfer.cs:136` with `SendTimeLimits.Stamp(transfer, limits, now);` placed before `transfer.Status = 1;` (the guard needs Status 0; the existing check at line 103 already rejects non-drafts, so the guard is defence in depth). Effect: MaxDownloads becomes the resolved plan value at send. Re-send drafts also go through SendTransferHandler, so they are covered too.
Not touched: the finalize / resend draft placeholders (`FinalizeTransfer.cs:139,143`, `ResendTransfer.cs:93`). Drafts are not downloadable and never expire (FR-005-1); send overwrites both fields. Replacing the placeholders would change the finalize response's expiresAtUtc (`FinalizeTransfer.cs:185`) — out of scope (section 5).

### D-3 — Which plan is resolved: unchanged here, owned by F-BIL-003
FR-020-1 / US-020-01 put "User → Plan → Limits" in a single PlanContextMiddleware and forbid commands from looking up the plan themselves. T-031-04 therefore does not add an AppUser.PlanId lookup to finalize/send (that would be the scattered plan check F-BIL-003 removes). Consequence: AC-018-3 / US-018-04 AC block 1 (plan switch) is encoded at the handler level — the provider stub returns Pro values for send 1 and Free values for send 2, proving the handler stamps whatever is resolved at that send and leaves the live row alone. The HTTP-level "pro user downgraded → next send gets Free limits" test lands with US-020-01, whose PlanContext feeds the same Stamp call. AC block 2 (flag raised) is exercised end to end on real SQL (step 4).

### D-4 — Live re-resolution outside the stamped fields (flagged, not changed)
`GetPublicTransferQuery.cs:90,96` (Download-all offer) and `src/wa.workers/ZipFunction.cs:80,84` (zip cap) resolve MaxZipSize at read time, so a flag edit to maxZipSize affects live transfers. Snapshotting it would need a new Transfer column the spec does not name → AGENT.md §7 escalation, raised as a non-blocking DECISION (section 5). This plan does not assume an answer and does not touch those files.

## 4. Open Questions / Risks

- **Behaviour change: download cap.** Transfers sent after this task carry the plan's MAX_DOWNLOADS (Free 100, Part 2) instead of the finalize placeholder 1. This implements the frozen constant (FR-003-5 "Downloads left: 87" assumes 100) and the US-018-04 technical note; it is not a limit-value change, so not escalated. Orchestrator: mention in the feature PR; the mobile.spec.ts:146 comment becomes stale (docs/e2e wording only).
- **Plan switch end to end** depends on F-BIL-003 US-020-01 (PlanContextMiddleware). Until then every send resolves the Free plan, so a Pro user's transfers are stamped with Free limits. Orchestrator: when planning US-020-01, require an HTTP-level AC-018-3 test (downgrade between two sends) and that PlanContext.Limits flows into the same SendTimeLimits.Stamp call.
- **Finalize/resend placeholders** (`FinalizeTransfer.cs:139,143,185`, `ResendTransfer.cs:93`) remain literals on draft rows (golden rule 2 smell, pre-existing). Harmless because send overwrites them, but the finalize response reports a 30-day expiry for a 7-day Free transfer. Candidate follow-up task; not in this story.
- **DECISION (non-blocking) — MaxZipSize live re-resolution:**
