## Description

The entire data model of ProtoDrop — every table that will exist at MVP and Phase 1/2/3 — is created in one migration, verbatim from the authoritative DDL in TA-3.2. `wa.domain` holds pure POCOs with zero external references; `WaDbContext` + entity configurations live only in `wa.infrastructure/Persistence`. The seed data (three plans with their limits JSON, and the full `FeatureFlag` set) ships as a second migration so that every environment — local Docker SQL, CI Testcontainers, dev/staging/prod — starts from the identical state. This is the foundation feature behind "schema changes are migrations" (golden rule 4): after T-004 there is no table without a migration and no entity without a home in the onion.

**Actors:** developer/AI session (writes code against the model), ops (runs migrations at deploy via TA-12.2), every later feature (reads/writes these tables).
**Value:** one schema, decided once; T-009 onward never invents a table — they use what's here or escalate for a new migration + ADR note.

## Functional requirements

| ID | Requirement |
|---|---|
| FR-052-1 | `wa.domain` contains POCO entities for every TA-3.2 table (BCL-only, no EF/Azure/MediatR references): Plan, AppUser, AuthToken, Transfer, BlobRef, FileItem, EmailRecipient, EmailSuppression, DownloadEvent, Subscription, StripeEvent, FeatureFlag, AuditLog, JobRun, IdempotencyKey — 15 entities, 1:1 to DDL columns. |
| FR-052-2 | `WaDbContext` + one `IEntityTypeConfiguration<T>` per entity live in `wa.infrastructure/Persistence`; the EF migration `InitialCreate` reproduces TA-3.2 **verbatim**: all PK constraint names, all 8 FK constraints (`FK_AppUser_Plan`, `FK_Sub_U`, `FK_T_Super`, `FK_Transfer_Owner`, `FK_ER_T`, `FK_FileItem_T`, `FK_FileItem_B` + self-reference), the 7 default clauses, both filtered indexes, `UQ_ES` / `UQ_Transfer_LinkId` unique constraints, and `IX_Transfer_Owner` (DESC) + `IX_Transfer_Expiry` INCLUDE per TA-3.2/TA-3.3. |
| FR-052-3 | Conventions per TA-3.1: all timestamps `DATETIME2` UTC suffixed `...AtUtc`; IDs are `UNIQUEIDENTIFIER` generated by clients; soft-delete only on `AppUser` and `Transfer` (`DeletedAtUtc`); money never stored in the DB (Stripe is truth). |
| FR-052-4 | Seed migration `SeedPlansAndFeatureFlags`: three `Plan` rows (free/pro/business, fixed GUIDs) with `LimitsJson`/`FeaturesJson` per Open-Decisions-and-Constants.md Part 2, plus the full seeded `FeatureFlag` set (12 `feature.*` gates defaulting false per D-14, and 3 × 14 `limits.<plan>.*` keys). |
| FR-052-5 | Migrations are the only schema mechanism: every later change is a new EF migration in `wa.infrastructure/Persistence` (TA-3.7); expand-first rule — add columns, never drop in the same release as code that needs them. |
| FR-052-6 | `dotnet ef database update` against local Docker SQL creates all tables and seed rows; the migration script (`migrations script -i`) cross-checks against TA-3.2 with zero drift. |

## Acceptance criteria

```gherkin
AC-052-1: A fresh local SQL instance is migrated
  Given docker compose (F-FND-002) is running and no wa schema exists
  When I run dotnet ef database update
  Then all TA-3.2 tables exist with the exact PK/FK constraint names from the DDL
  And the filtered indexes and unique constraints are present

AC-052-2: Seeds are identical everywhere
  Given a migrated database (local, CI Testcontainers, or dev)
  When I query Plan and FeatureFlag
  Then exactly 3 plans exist with Part-2 limits JSON
  And all seeded flag keys resolve (12 feature gates + 42 limit keys)

AC-052-3: The domain layer stays pure
  Given wa.domain compiles
  When I inspect its references
  Then it has zero external NuGet/project references (BCL only)

AC-052-4: No drift between DDL and migration
  Given the InitialCreate + seed migrations
  When I script them to SQL (dotnet ef migrations script -i)
  Then the result matches TA-3.2 verbatim (constraint names, defaults, indexes)
```

## Edge cases

| ID | Case | Behavior |
|---|---|---|
| EC-052-1 | `ON DELETE` not specified on FKs | EF omits it = SQL Server default `NO ACTION`, which matches the DDL (T-004 note) — do not "fix" it by adding CASCADE |
| EC-052-2 | A later feature needs a new table | New migration + ADR note in TA-17 (golden rule 4); never hand-edit SQL in prod (TA-3.7) |
| EC-052-3 | Seed values change (e.g. limits re-tuned) | Part 2 constants are frozen — changing them is a decision request (AGENT.md §7), not a code edit; seeds follow the confirmed value |
| EC-052-4 | Migration runs on a database with data | Expand-first: additive changes only in the release that needs them (TA-3.7) |

## Technical notes

- 15 POCOs in `wa.domain` (T-004 deliverable); `LimitsRecord` joins later with T-005 (F-FND-005).
- EF Core 10.x is the only EF home: `WaDbContext`, configurations, and migrations all in `wa.infrastructure/Persistence`.
- Fixed GUIDs for plan seeds keep FK values stable across environments (test fixtures reuse them — TA-14.3).
- T-004 exit evidence: `out.sql` cross-checked against TA-3.2; integration test `SeedDataIntegrationTest` (Testcontainers) asserts the seeds end-to-end.
