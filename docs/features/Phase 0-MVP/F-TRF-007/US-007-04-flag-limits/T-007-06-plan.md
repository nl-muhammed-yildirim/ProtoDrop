# T-007-06 — Implementation Plan

## Goal
Add an integration test proving FR-007-5 end-to-end against a real database via the API surface: with `limits.free.maxTransferSize` at 5 GB a 6 GB draft is rejected with `TRANSFER_SIZE_EXCEEDED`; after upserting the flag to 10 GB and waiting out the real 30 s TTL, a new 6 GB draft is accepted — no deploy in between; and an already-finalized transfer keeps its send-time values (EC-007-1). Exit check: both US-007-04 Gherkin behaviors hold through the draft/send endpoints with no deploy.

## Design & Decisions
- **One new test class, zero production-code changes**: `tests/wa.api.integration/FlagOverrideIntegrationTests.cs`. The Limits Registry, flag-override precedence (`LimitsProvider`), and DI wiring are all in place from T-007-01/02 — this task is purely a test that pins the end-to-end flow.
- **Test surface = HTTP only** (exit check: "assert via the API surface, not by poking the provider directly"): requests against `POST /api/v1/transfers/draft` (TA-4.2#1) and `POST /api/v1/transfers/{id:N}/send` (TA-4.2#3); DB (`_db.Set<FeatureFlag>()`, `_db.Set<Transfer>()`) is used for the flag upsert — which T-024's admin endpoint 23 will replace later — and for post-hoc Status/TotalBytes assertions, same convention as existing integration tests (TA-14.3 harness: fresh Azurite + SQL 2022 per instance via Testcontainers).
- **TTL strategy — real wait, not a fake clock**: the task allows "fake clock or real wait per test harness convention"; the repo has no fake-clock injection in the integration harness (`FlagsCache`/`PlansCache` get their TTL from `Wa:Flags:TtlSeconds` in `Program.cs`, default 30 s — TA-3.4). Shortening via env var would violate the explicit constraint "do not shorten it to make the test pass", so each fact that needs a cache refresh does exactly one real wait of TTL + 1 s (≈31 s), timed from the request that warmed the cache so elapsed is asserted ≥ 30 s.
- **Single-file 6 GB draft payload**: declared `sizeBytes = 6442450944` in one file entry — no blob upload needed at draft (enforcement happens on the request, no blob read), and single-file keeps the assertion isolated to MAX_TRANSFER_SIZE so maxSingleFile (also seeded 5→10 GB) can't mask it. Rejection is asserted as the TA-4.1.3 closed-list shape: HTTP 422 + `code == "TRANSFER_SIZE_EXCEEDED"` + both numbers in details (pattern pinned by the T-007-02/04 tests).
- **EC-007-1 mechanics**: a small transfer (512 B) is draft → staged-blob upload → finalized *before* the flag edit, then sent *after* the TTL wait; it must succeed with its own send-time values (Status 0→1, TotalBytes unchanged). This proves only new resolutions pick up the change — the in-flight row never re-resolves against a stale limit.
- **No NuGet package added, no migration, no EF model change** → golden rule 1 (TA-17) and TA-2.3 satisfied by construction.

## Implementation Plan
Ordered steps for the coder — all under `tests/wa.api.integration/`:

1. **Create `FlagOverrideIntegrationTests.cs`**, xunit class mirroring `SendEndpointTests.cs` layout:
   - Class-level constants with comments "values per seeded flag row, not plan literals (TA-3.4)": `FreeMaxTransferSize = 5_368_709_120L`, `TenGb = 10_737_418_240L`, `SixGb = 6_442_450_944L`.
   - `InitializeAsync()`: start `AzuriteContainer` + `MsSqlBuilder("mcr.microsoft.com/mssql/server:2022-latest")` exactly as in `SendEndpointTests.cs:32-62`; set the same env vars (`Wa__Blob__*`, `Wa__Jwt__Secret`, `Wa__Url__Public`, dummy Service Bus connection, `ConnectionStrings__WaDb`); create staging/transfers containers; `_db` context + `MigrateAsync()` (seeds the 5 GB flag row via migration `20261011215315_SeedPlansAndFeatureFlags`); `new TestFactory().CreateClient()`.
   - `DisposeAsync()` disposes db, sql, azurite. Nested `private sealed class TestFactory : WebApplicationFactory<Program> { }`.

2. **Helpers** (same file):
   - `UpsertFlagAsync(string key, string value)` — EF upsert on `wa.domain.FeatureFlag` (`Key` is the PK): update existing row's `Value` + `UpdatedAtUtc`, insert if absent; returns the stored value so tests can assert it.
   - `PostDraftAsync((string name, long sizeBytes)[] files)` → POST `/api/v1/transfers/draft` with `{ files = [{ name, sizeBytes, contentType: null }] }`; returns the response (caller asserts status + shape).
   - `SetupFinalizedTransferAsync(long sizeBytes)` — copy of `SendEndpointTests.SetupDraftTransferAsync`: draft → upload random bytes to staging at the canonical split path (`stagingPath[..cut]` container / rest blob) → finalize with a fresh `Idempotency-Key`; returns transfer id.
   - `PostSendAsync(Guid transferId, object body, string idempotencyKey)` — copy of existing helper (unique key per test).

3. **Test 1 — `[Fact] Flag_Override_Draft_RejectedAt5GB_AcceptedAfter10GB_NoDeploy`:**
   - Assert the seeded flag row reads `"5368709120"` (guards the fixture).
   - POST 6 GB draft → assert `HttpStatusCode.UnprocessableEntity`, body `code == "TRANSFER_SIZE_EXCEEDED"`, status field `422`; start a stopwatch on this response (the request that warmed `FlagsCache`).
   - Upsert flag to `"10737418240"`; assert stored row value.
   - `await Task.Delay(31_000)`; assert elapsed ≥ 30 s (pins the "real TTL, not shortened" constraint).
   - POST a **new** draft with the identical 6 GB single-file payload → assert success status and TA-4.2#1 shape: top-level `draftId`/`expiresInSec`/`files`, one file row — acceptance at the new limit with no other change in between (the "no deploy" property).
   - Verification: `dotnet test tests/wa.api.integration --filter Flag_Override_Draft_RejectedAt5GB_AcceptedAfter10GB_NoDeploy`.

4. **Test 2 — `[Fact] In_Flight_Transfer_KeepsSendTimeValues_AfterFlagEdit`:**
   - Finalize a 512 B transfer via `SetupFinalizedTransferAsync` (under the seeded 5 GB flag).
   - Upsert flag to `"10737418240"`, wait out TTL exactly as in step 3.
   - POST `/send` with one email → assert 201, body `status == "Active"`, DB row `Status == 1`, `TotalBytes == 512` unchanged — the transfer was resolved with its own send-time values; only new resolutions pick up the change (EC-007-1).
   - Verification: `dotnet test tests/wa.api.integration --filter In_Flight_Transfer_KeepsSendTimeValues_AfterFlagEdit`.

5. **Gate** (`docs/AGENT.md` §4): `dotnet build`, then the full task gate — `dotnet test tests/wa.domain.unit && dotnet test tests/wa.application.unit && dotnet test tests/wa.api.integration` (Docker must be running). Both new tests plus existing ones green; commit as one: `feat: T-007-06 flag override integration test`.

## Open Questions / Risks
- **Wall time**: the two TTL waits add ~62 s to the suite (plus container startup). Per PROGRESS.md the slow api.integration suite only runs at the feature review point, so this is acceptable now; if it ever becomes a CI bottleneck, TTL injection via the `Wa:Flags:TtlSeconds` env var in tests is the sanctioned follow-up — not this task.
- **Pre-existing failure**: PROGRESS.md notes a pre-existing `PublicTransferEndpointTests` failure at base b788f21 — treat as out of scope for this commit; report it if it recurs rather than fixing inline (keep the commit bounded to the backlog row).
- **Spec wording**: the task says "wait out the 30 s cache TTL … a new 6 GB draft is accepted"; the plan interprets "accepted" at the *draft* endpoint per the explicit constraint line ("assert via the draft endpoint"). If the reviewer prefers acceptance asserted at finalize/send instead, the flag-upsert + TTL pattern in steps 3/4 is identical — no design change needed.
- **Constants check**: values match the migration seed (5 GB) and TA-3.4's 30 s TTL — both verified against source before planning; no Open-Decisions Part 1–2 conflict found.
