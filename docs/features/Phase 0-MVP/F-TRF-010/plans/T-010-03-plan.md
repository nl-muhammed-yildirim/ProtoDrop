## ASSUMPTIONS

- **Password field starts empty always.** Endpoint 16 returns `passwordRequired: bool` but NOT the plaintext (PBKDF2 is one-way). "Pre-filled" in US-010-02's AC means the field is present, active, and labeled to indicate a password was set on the original — not that the value itself is recoverable. The user re-enters or clears; there is no "keep original password" option (documented below).
- **C# fix resolves both PBKDF2 keying and AC-010-2 "clearing → unprotected."** T-010-01 copies the original's PasswordHash byte-for-byte into the new draft. That hash was keyed by `originalTransferId.ToString("n")` at its creation time (SendTransfer.cs L155). UnlockTransfer.cs L73 verifies against `newDraftId.ToString("n")`. Without intervention, every re-sent transfer with a password would fail unlock. The fix: when `/send` processes a SourcedFrom draft and no new password is provided, set PasswordHash = null (treat as explicit clear). This means the user MUST re-enter the password for it to be protected on the new transfer — leaving it blank = unprotected. This matches US-010-02's "Change password to empty: the new transfer is unprotected" and avoids shipping a stale-keyed hash that would break every unlock attempt.
- **No separate "keep original password" option in MVP.** Since PBKDF2 can't be re-keyed without plaintext, keeping the copied hash would require either (a) storing plaintext somewhere or (b) re-hashing at send time with the new ID using a sentinel that says "same as before." Neither exists. For MVP: blank field = unprotected; entered value = new password keyed correctly by this draft's ID. If product wants "keep same password," that's a follow-up task requiring either a C# column for plaintext or an endpoint 16 addition returning the original password (security trade-off).
- **LinkScreen is not yet mounted in production.** App.tsx renders DropZone + StagingList at `/` with no sender link-screen route. T-010-03's ReSendScreen is the FIRST production mount of LinkScreen (via its pre-fill props). The normal post-upload "link ready" screen (T-002-04) was built but never integrated into routing — that integration is a separate task (likely T-010-04 or later).
- **Route format `/resend/{transferId}` uses the ORIGINAL transfer's ID** (the one from My Files rows, endpoint 14). Endpoint 16 mints a NEW draft with its own LinkId — that new linkId is what appears in the post-send confirmation URL. The route param is the original because that's what the user clicked Re-send on; the screen then calls endpoint 16 to create the draft and gets back the new transferId + linkId for /send.
- **No new packages.** React, existing CSS variables (--accent-soft, --fs-small), and hand-written tests only. No router library (App.tsx uses pushState + popstate pattern).
- **Banner copy exact strings:** fileCount === 1: "Re-sending '{name}'. You can change the details before sending." | fileCount > 1: "Re-sending '{firstFile}' and {count - 1} more files. You can change the details before sending." (EC-010-3 all-or-nothing — no per-file selection UI in MVP; the banner conveys it).
- **FILES_GONE state is screen-level, not form-level.** When endpoint 16 returns 410, ReSendScreen renders a completely separate single-screen layout (no LinkScreen at all) — "Files were deleted — upload again." + Upload primary → `/`. This avoids the "half-filled form" anti-pattern from the exit check.
- **The C# change in SendTransfer.cs is scoped to re-send drafts only** (`transfer.SourcedFrom is not null` guard). Normal drafts (SourcedFrom = null) are untouched — their existing unit tests pass unchanged because the new branch never fires for them.
