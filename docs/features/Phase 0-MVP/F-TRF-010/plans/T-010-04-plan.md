# T-010-04 Implementation Plan

TASK: T-010-04 Storage meter counts unique BlobRefs — no double-count on re-send (FR-010-1, AC-010-1 blob-sharing clause; milestone row T-023 part 4)

GOAL: The per-user active-bytes expression that T-007-03's quota check and T-007-05's meter both read must count **unique BlobRefs**, not transfer rows or FileItem rows. Today it sums Transfer.TotalBytes per active row, so a 2 GB transfer re-sent N times counts as N×2 GB (the re-send creates new FileItem rows pointing at the SAME BlobRefId(s), and the original's Status is left unchanged by SaveSendAsync — only SupersededBy is set). Fix: join Transfer → FileItem → BlobRef, dedupe by BlobRefId, sum BlobRef.SizeBytes where the transfer is active (Status IN (1,3)). A 2 GB transfer re-sent 10 times still counts as 2 GB. Deletion path stays as-is (T-009-04's endpoint 17 already decrements RefCounts and sets the 24 h buffer at 0); this task only proves the round-trip holds.

## ASSUMPTIONS

- **The admin storage_bytes_active metric has no separate query in src/ today.** A repo-wide grep for the active-bytes expression finds only per-user GetActiveStorageBytesAsync (TransferStore.cs L24) and its two callers (FinalizeTransfer.cs L105, SendTransfer.cs L204). The story's "admin storage counter" is F-TRF-011-2 territory (not yet built). DECISION: do NOT invent a forked admin query in this task — when F-TRF-011-2 builds the cross-user total, it must sum over BlobRef with Distinct-by-BlobRefId (the same idiom as file #1), not per FileItem. The per-user fix here is what T-023 part 4 verifies; the admin variant inherits correctness by reusing the idiom.
- **The quota check formula is unchanged — only the expression it reads changes.** FinalizeTransfer.cs L105 still computes activeBytes + totalBytes > limits.StorageQuota. DECISION: scope file #1 to the shared expression (per task bullet 1, "one query, reused everywhere"). KNOWN LIMITATION recorded for review: at the exact limit boundary, re-sending a file whose blob is already counted in activeBytes still adds its full totalBytes to the check (the check treats the re-send's bytes as new even though they are shared). The meter stays correct (unique-BlobRef sum); the quota check is conservatively strict. If product wants re-sends to be quota-free at the boundary, that is a follow-up requiring activeBytes + (totalBytes − already-held-bytes), not part of this task's "one expression" constraint.
- **Re-send leaves the original's Status unchanged.** SaveSendAsync (SendStore.cs L42-52) sets SupersededBy on the original via raw SQL but does NOT change its Status, so both original and re-send remain in the active set (Status IN 1,3). The unique-BlobRef dedupe is what prevents double-counting — we do not rely on a Status flip or a SupersededBy IS NULL filter. This matches T-010-01's design (linear SupersededBy per transfer) and means the new test must seed BOTH rows as active to reproduce the bug it fixes.
- **EF Core translates the three bounded queries to one subquery.** Set<BlobRef>().Where(b => blobIds.Contains(b.Id)).SumAsync with blobIds = a Distinct subquery over FileItem/Transfer compiles to SUM(SizeBytes) WHERE Id IN (SELECT DISTINCT BlobRefId …). This is the same subquery-in-Contains idiom already used by ListByOwnerAsync's RecipientCount scalar subselect (TransferStore.cs L66), so no N+1 and no new translation risk. If the coder's EF version does not fold it, three round-trips on a per-send meter read is still bounded and acceptable for MVP (flag if a perf regression surfaces).
- **SumAsync over an empty set returns 0** — same as the existing expression (which also SumAsync'd Transfer.TotalBytes with no rows guard), so a brand-new account reads 0 bytes; no new edge introduced.
