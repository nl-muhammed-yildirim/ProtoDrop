# T-009-03 Implementation Plan

TASK: T-009-03 GetMyTransferQuery + endpoint 15 — owner detail incl. per-file rows and recipient list (TA-4.2#15)

GOAL: GET /api/v1/transfers/{id} (cookie required) returns the signed-in user's transfer detail — everything in a T-009-01 list row (name, file count, total bytes, status, expiry, download count + cap, recipient count) PLUS the per-file rows (name, size) and the recipient list (EmailRecipient addresses). Owner scope: the row must belong to the session user id — foreign owner, guest-created (OwnerAppUserId=NULL), deleted (DeletedAtUtc set), or unknown id all return the identical 404 Problem+JSON NOT_FOUND body (no FORBIDDEN, no enumeration between accounts). AC-009-1 applies: bounded queries only — one aggregate fetch, no extra round-trips per row (FR-009-1 detail; FR-009-3 backs the row actions copy-link / view / re-send / delete).

## ASSUMPTIONS

- Detail record choice (explicit): GetMyTransferResult COMPOSES the existing MyTransferRow plus Files + Recipients rather than a flat duplicate of all row fields — one source of truth for the T-009-01 row payload; the endpoint JSON mirrors T-009-01's exact wire names so UI code treats list rows and detail identically.
- Recipient list = addresses only (EmailRecipient.Address), ordered by Id; NotifiedAtUtc / PreferredLanguage are not part of FR-009-3 row actions at MVP — no extra fields invented.
- File rows carry name + sizeBytes only per the spec ("per-file rows (name, size)"); file ids stay internal until a future download-from-detail action lands.
- Null-result pattern mirrors SendTransfer (T-008): handler returns `GetMyTransferResult?` and Program.cs throws BusinessException(NotFound) on null — no new exception types in the application layer.
- Owner scope is enforced by the store's single-row predicate, NOT by a second existence check — that is what makes foreign-owner / deleted / guest bodies identical.
