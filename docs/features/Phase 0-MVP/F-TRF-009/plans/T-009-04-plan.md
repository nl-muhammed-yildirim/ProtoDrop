# T-009-04 Implementation Plan

TASK: T-009-04 DeleteTransferCommand + endpoint 17 — owner delete, refcount path (FR-009-3)

GOAL: DELETE /api/v1/transfers/{id} (cookie required) soft-deletes the signed-in user's transfer. Owner scope: the row must belong to the session user id — foreign owner, guest-created (OwnerAppUserId=NULL), already-deleted, or unknown id all return the identical 404 Problem+JSON NOT_FOUND body (no FORBIDDEN, no enumeration). AC-009-2 applies server-side. On success: mark row Status=4 Deleted with DeletedAtUtc set (NOT a hard delete); emit transfer.deleted ({transferId, reason:"user"}) once via the outbox IEventPublisher; decrement each FileItem's BlobRef RefCount; when a blob hits 0 set PhysicallyDeletedAtUtc = now + 24 h (the SAME buffer as the F-TRF-005 expiry path — TA-6.5 / Part 2 "Blob delete buffer"). Idempotent delete EC-009-2: a second request for an already-deleted row returns NOT_FOUND, which the client treats as success (no 409, no special code). Quota frees immediately because Status=4 drops the row out of the FR-007-4 meter; in-flight 30-min SAS URLs keep working (SAS outlives the row — EC-009-1). Delete is NOT subject to the grace window (owner intent > grace). Admin force-delete later reuses this same command with reason "admin" (US-011-02) — one command, two reasons.

## ASSUMPTIONS

- MarkDeleteResult record choice (explicit): the store returns a small sealed record `MarkDeleteResult(DateTime DeletedAtUtc, string LinkId)` rather than just a bool or DateTime? — this gives the handler the LinkId it needs to partition the outbox envelope EXACTLY like SendTransfer.cs:167 does (PartitionKey = LinkId). Defining the record in DeleteTransferCommand.cs (not ITransferStore.cs) keeps the interface additive-only and avoids a circular reference.
- Reason is payload-only, NOT persisted: grep of src/wa.domain/Transfer.cs + all EntityConfigurations + Migrations confirms no DeletedReason / DeletedBy / Reason column exists on the Transfer entity or in any migration. The task spec says "mark row Deleted (reason 'user')" but the only place reason appears at runtime is the event payload — this matches SendTransfer's precedent where all mutation context lives in the envelope, not a DB column. If a later admin audit task needs to query by reason, that's a schema change for THAT task, not T-009-04.
- No grace window applies to owner delete: the spec says "delete is not subject to the grace window (owner intent > grace)." The grace window (TA-3.5 staging lifecycle 24 h) is about blob staging before a transfer becomes visible — it does NOT apply to a row that is already sent/active/expired and being deleted by its owner. No code change needed; the absence of any grace-window check in the handler IS the implementation.
- Status=4 makes the recipient page die without any public-store change: GetPublicTransferQuery.cs:70 already maps `transfer.Status == 4` → NotFound (FR-003-9), so once the row flips to 4, the next GET /api/v1/t/{linkId} returns the same 404 body as an unknown link. No FileItem/EmailRecipient hard-delete in the owner path — that cleanup stays with the F-TRF-005 expiry job (ExpiryDeletionStore.cs:87-99) which runs on a schedule and owns the row-cleanup responsibility.
- Endpoint 17 returns 204 No Content, NOT 200 JSON: delete semantics — the client does not need the row back (it already has it from endpoint 15). This differs from T-008 send (which returns 200 + result body because the caller needs the linkId/recipient list). 204 is consistent with how DELETE endpoints behave in this codebase (admin suppression at Program.cs:381 uses Results.Ok() but that's a legacy shape; the modern thin-endpoint convention per TA-4.2a is minimal response).
- Envelope correlation ID via GetCorrelationGuid() verbatim from SendTransfer.cs:193 — W3C trace-id 32-hex → Guid, fallback Guid.NewGuid(). This pins the event to the request that triggered it (AC-054-2 byte-exact serialization; no per-call options).
- One command, two reasons: DeleteTransferCommand takes a Reason string parameter pinned to "user" at endpoint 17. US-011-02's admin force-delete will construct the same record with reason "admin" — no new command, no new handler, just a different construction site. The store does NOT take reason (it is payload-only), so the signature stays stable for both call sites.
